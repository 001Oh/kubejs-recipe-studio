# 架构决策

需求规格第十章要求先说明架构再开工。下面是本项目全程遵循的七条决策，实现过程中若与规格冲突，以规格为准并回来更新本文件。

## 1. 进程划分

主进程独占文件系统、zip 解析与 worker 编排：整合包导入、jar 扫描、配方解析、schema 反推、代码生成、插件加载全部在
主进程；渲染进程是纯 React，`nodeIntegration: false`、`contextIsolation: true`、`sandbox: false`，拿不到任何 `fs` 或
`require`。扫描类重活在 `worker_threads` 池里跑（并发 = `os.cpus().length`，上限 8），主线程不阻塞，worker 产物经
`electron.vite.config.ts` 的额外入口编译成 `out/main/scan.worker.js` / `recipe.worker.js`。

## 2. IPC 设计

只有一条请求通道 `studio:invoke` 与一条事件通道 `studio:event`。请求按 `InvokeMap`（`src/shared/ipc.ts`）做名字到
请求/响应类型的映射，返回值一律 `{ ok: true, data } | { ok: false, error, code? }`；主进程 handler 统一被
`ipcRegistry` 的 try/catch 包住，异常转成错误对象，绝不向渲染进程抛未捕获异常。进度与日志通过事件单向推送，渲染端
不轮询。新增操作必须先在 `InvokeMap` 登记，禁止散落裸 channel。

## 3. 目录结构

`src/main`（`modpack/ scanner/ recipes/ schema/ codegen/ plugins/ cache.ts logger.ts paths.ts ipcRegistry.ts
scanControl.ts window.ts handlers/`）、`src/preload`、`src/renderer/src`（`views/ components/ store/ hooks/ styles/`）、
`src/shared`（`types.ts ipc.ts constants.ts` 与纯算法）、`tests/`。约定：单个文件不超过 300 行；每个领域在自己的
`handlers/xxxHandlers.ts` 里导出 `registerXxxHandlers()`，由 `handlers/index.ts` 集中接线。

## 4. 物品索引与图标

`mods/*.jar` 流式读取（`yauzl`，不全量解压），worker 内产出物品摘要，主进程汇总后写
`userData/cache/<sha1(整合包路径)>/items.json`，内含中文名、英文名、`modId`、置信度、`virtual` 标记、预计算的
`pyFull` / `pyInitials`。图标以 16×16 原尺寸 PNG 落 `userData/icon-cache/<sha1(物品ID)>.png`，由自定义协议
`app-icon://<sha1>` 提供，前端 `image-rendering: pixelated` 且只做 16→32→48 整数倍放大。失效判据是 mods 目录的
`mtime + jar 数量 + 总字节数`，外加 MC / KubeJS 版本，命中缓存时二次启动直接读 JSON。

## 5. 配方摘要与倒排索引

扫描阶段只存摘要 `RecipeRecord`（`type` / `outputs` / `inputs` / `source` / `sourcePath` / `partial`），完整 JSON
不入内存也不落盘。主进程持有 `records: RecipeRecord[]` 与 `byOutput` / `byInput: Map<string, number[]>` 两张倒排表，
「制作」与「用途」是同一份索引的两次查询。渲染端通过分页查询拿切片（`offset` + `limit`），永远不会把十几万条记录整体
下发。持久化到 `cache/<hash>/recipes.json`，与物品索引同生命周期失效。

## 6. Schema 注册表

主进程按 `Map<typeId, RecipeTypeSchema>` 组织，来源优先级：用户钉住 > 插件 > L0 内置库 > L2 class/ProbeJS 解析 >
L1 反推；L1 同时对上层骨架做字段校验与补全（出现率 ≥10% 的实测字段追加为可选，骨架有但样本里从没出现的降级到「高级」
区）。渲染端只按 11 种 `kind` 渲染控件，代码里不存在按配方类型分支；`unknown` 一律进「高级参数」键值编辑器，完全无法
解析时退到纯 JSON 编辑器，三级降级永远可用。

## 7. 生成与惰性读取

emitter 三条通道（`kubejs-sugar` / `event-custom` / `datapack-json`）由 schema 的 `emitTarget`、附属模组检测结果与
字段 `sugarSupported` 共同决定，默认「能跑通」优先：附属缺失即自动切数据包 JSON，绝不为了代码好看赌一把语法糖。写盘前
跑 acorn 语法预检与基于 schema 的语义校验。用户点开配方卡片要完整 JSON 时，才用 `yauzl` 按 `sourcePath` 打开对应 jar
读那一条（读一条关一次，不复用句柄），失败按 `ENOENT` 提示源文件已失效。

## 虚拟物品：查询期过滤（2026-10-31 决策，替换建库期过滤）

**决策**：物品索引与搜索语料保存**全部**符合索引条件的物品（含 `ritual_dummy` 等虚拟物品）；
是否显示只由查询参数 `ItemsQuery.includeVirtual` 决定。

- 唯一定义：`src/shared/ipc.ts` 的 `ItemsQuery.includeVirtual?: boolean`（默认 false = 隐藏）。
  UI、扫描器、搜索算法都只认这一个字段，不在各自模块里再设开关。
- 判定规则：`src/shared/search.ts` 的 `isVirtualItem()` 是唯一实现——显式 `virtual === true` 直接生效，
  否则按规格 3.6.13 的路径/命名规则补判；不做第三种猜测。
- 语料不因显示设置而丢弃条目（`buildSearchCorpus(items)` 不再接受 `includeVirtual`）。

**三类缓存各自失效，互不牵连**：

| 缓存 | 位置 | 失效条件 |
|---|---|---|
| 物品扫描结果 | `studio-cache/<hash>/items.json` | mods 签名（mtime+数量+字节）、MC/KubeJS 版本、`PARSER_VERSION`。**不看 extras**：物品只来自 mods jar |
| 配方摘要 | `studio-cache/<hash>/recipes.json` | 上述全部条件 **+ `extras`**（kubejs 脚本、kubejs/data、openloader、datapacks 都会改变配方） |
| 搜索语料 | 进程内存（由 items 构建） | 只随物品索引重建；**与显示设置无关** |
| 用户查询设置 | `userData/uiState.json` 的 `showVirtualItems` | 只影响下一条查询的参数 |

`meta.json` 记录 `phases`（`items` / `recipes`），只有全部阶段成功才写入；
下一次启动按所需阶段逐一校验，缺哪个就补哪个。因此改一个 KubeJS 脚本只会重扫配方，不会重扫物品。

因此切换虚拟物品显示：不重扫、不重建语料、不作废任何缓存，只换查询参数。
若将来把语料持久化，它只能依赖 items 索引的版本，**不得**把 `showVirtualItems` 写进它的键。

## 与规格的两处有意偏离

1. **视图切换键**：规格 3.9.9 同时要求「`Tab` 遍历焦点」与「`Tab` 切换配方浏览/工作台」，两者互斥。实现取可访问性优先，
   视图切换改用 `Ctrl+Tab`，裸 `Tab` 留给键盘焦点遍历。
2. **注册表槽缩写角标**：`INF` / `GAS` / `SLR` / `PGM` 之外，遇到未知注册表类型统一用 `REG`，避免为每个模组枚举缩写。

两处都会在 README 的「已知取舍」里向用户说明。
