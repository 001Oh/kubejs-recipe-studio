### 2.1 BH-013 · 插件 manifest 缺数量上限

| 项 | 内容 |
| --- | --- |
| **原始编号** | BH-013（BUG-HUNT-01）；BUG-HUNT-02 列为"未处理（需决策）" |
| **当前状态** | **仍未解决，暂缓处理**（源码未改） |
| **证据** | `src/main/plugins/manifest.ts` 的所有数组解析（`parseSlotList` / `recipeTypes` / `virtualItemPatterns` / `mods`）**均无长度上限**；对比 `hookSandbox.ts:19` 有 `HOOK_SOURCE_MAX_BYTES`，说明作者对体积有意识，但 manifest 没有对应约束 |
| **风险等级** | **P3** |
| **影响** | 恶意或误生成的超大 manifest 会让 `buildPluginSchema` ×N 与类型选择器渲染变慢；插件是本地文件，攻击面有限；**不涉及数据安全** |
| **尚缺的验证条件** | 需要一份真实量级的对照：正常插件最大声明多少个 `recipeTypes`？现有插件生态里有没有 >100 的？没有这个数就无法定阈值 |
| **暂缓原因** | 任务明确要求"采用与项目现有架构一致的约束，**不要凭空引入不合理的硬编码限制**"。当前没有任何证据支持某个具体阈值；贸然加 `MAX_TYPES=128` 有可能直接废掉一个合法的大型整合包插件 |
| **建议后续处理** | ① 统计 3–5 个真实插件包的 `recipeTypes` 数量分布；② 若确有 >500 的实例，则上限应设为"远高于真实峰值"（如 2000）并只 WARN 截断、不拒绝；③ 同时给 `manifest.json` 文件大小加一个宽松上限（如 2 MB），这与 `HOOK_SOURCE_MAX_BYTES` 的既有风格一致，风险最低 |

### 2.2 BH2-003 · `{id, count}` 可能被误判为 blockstate

| 项 | 内容 |
| --- | --- |
| **原始编号** | BH2-003（BUG-HUNT-02 新发现） |
| **当前状态** | **仍未解决，暂缓处理** |
| **证据** | `src/main/schema/primitives.ts` `looksBlockstate()`：当对象有 `id`（形如 `ns:path`）且**任一**其它属性是 string/number/array/object 时返回 `true`。因此 `{ "id": "minecraft:stone", "count": 3 }` 会被判为 `blockstate`，`count` 被当成方块属性 |
| **风险等级** | **P3**（仅在 `augment`/推断链路上影响字段控件形态；不影响写盘正确性——`preserveUnknown` 仍保留原字段） |
| **影响** | 该字段在表单里被渲染成"方块状态编辑"而不是"物品 + 数量角标"；用户仍可通过高级 JSON 区手工修正 |
| **尚缺的验证条件** | 需要真实整合包统计：① `{id, count}` 形态的物品字段有多常见；② `{id, facing}` 形态的真 blockstate 有多常见。二者结构上不可区分，**阈值只能靠数据分布定** |
| **暂缓原因** | 收紧会**误伤真 blockstate**（`{"id":"minecraft:oak_stairs","facing":"north"}` 的 `facing` 就是普通字符串）。当前没有样本能证明收窄是净收益 |
| **建议后续处理** | 一个低风险的候选特例：把 `count` / `Count` / `amount` / `size` 从"可作为 blockstate 属性"的名单里排除（已有 `QUANTITY_KEYS` 常量可直接复用），因为这三者几乎不可能是方块状态属性。需先用真实样本验证不误伤 |

### 2.3 BH2-005 · 数量侧接受任意字符串

| 项 | 内容 |
| --- | --- |
| **原始编号** | BH2-005（BUG-HUNT-02 新发现） |
| **当前状态** | **仍未解决，暂缓处理** |
| **证据** | `src/main/schema/primitives.ts` `siblingHasQuantShape()`：`const numeric = field.shapeCounts.number + field.shapeCounts.string`；随后 `if (quant !== 'chance') return true` —— 即 `count`/`amount` 只要出现过字符串就认为合格；而 `chance` 分支额外要求"字符串必须可转数字" |
| **风险等级** | **P3** |
| **影响** | `{ item: 'x', count: 'abc' }` 也会被配对合并成"物品 + 数量角标"，UI 用数字框编辑，写回时类型从字符串变数字 |
| **尚缺的验证条件** | 需要真实样本确认：① `count`/`amount` 出现非数字字符串的比例；② 是否存在 `"1x"`、`"2 个"` 这类带单位的写法（若存在，现有合并**本身就是错的**，不只是字符串判断问题） |
| **暂缓原因** | 与 `chance` 分支的不对称确实可疑，但统一口径会改变字段分组结果（同一类型的表单布局变化），属**产品语义变更**，不能凭"看起来更严格"就改 |
| **建议后续处理** | 可先做**只告警不改行为**的探测：在 `augment` 时记录"数量侧出现非数字字符串"的 typeId 与样例，跑一轮真实整合包看命中率，再决定是否收紧 |

## 3. 确认不构成缺陷（1 项）

### 3.1 BH2-004 · `kindForField` 缺 `list` 分支

| 项 | 内容 |
| --- | --- |
| **当前状态** | **确认不构成缺陷**（源码推导 + 逐项代入） |
| **证据** | `infer.ts` `kindForField()`：当元素本身是数组时，`classifyPrimitive(levelOf(f))` 返回 `'list'`，五个 `if` 均不命中，落到 `shapeCounts` 兜底。代入"元素全是数组"：`c.string+c.number+c.boolean === 0` → 跳过混合判断 → `c.boolean===0` → `c.number===0` → `c.string===0` → 返回 `c.object > 0 ? 'struct' : 'unknown'` = **`'unknown'`** |
| **判定理由** | `'unknown'` 正是"无法用 11 种控件表达 → 归入高级 JSON 编辑"的设计出口；`FieldKind` 本身**没有** `'list'` 成员。增加 `'list'` 需要同时改 `FieldKind` 联合类型、`fieldModel.tierOf`、UI 控件分支 —— 收益只是换一个更精确的名字 |
| **风险等级** | 无（不产生错误行为） |
| **后续建议** | 若将来要支持嵌套数组编辑，应作为**功能需求**（新增 FieldKind + UI），而不是当作缺陷修 |
