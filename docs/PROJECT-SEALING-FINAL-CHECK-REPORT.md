## 2. 确实存在的问题（11 项）

### F-01 `§1.1`"原始条目 40"不是原始条目，计算过程不可从原始报告复算 —— 中

- **位置**：`§1.1` 表，第 40 行（步骤①）
- **事实**：步骤①写"原始条目：C7 7 + OPT4 8（含 C1）+ UI 5 + P0 6 + P1 4 + P2 9 + REL-PKG 1 = **40**"。但按原始报告逐条重建：OPT4 为 **9**（`P-OPT4-最终验收` §4 有 8 条风险 + §5 的 C1）、UI 为 **6**（`UI` §10 有 U1–U6）、P1 为 **5**（`P1` §六"未完成"有 5 条），合计应为 **43**。
- **为什么算问题**：该行的标题是"原始条目"，第 40 行的用途是让人从报告复算。三个分组数其实已经扣掉了合并，于是 ① 被虚减 3 条；此时步骤②–④ 又只减了 3 条（R1、PKGDIR、C1），恰好回到 37。**两个错误相互抵消**：最终数正确，过程不成立。任何按报告复算的人都得 43，与台账写的 40 对不上。
- **最小修订**：把步骤①改为 43，并在②–④ 之间补三条归并记录（见 F-01b），或在① 的标题改为"去重后条目（部分分组已含合并）"并在 OPT4/UI/P1 三个分组数后注明已扣项。

### F-07 `REL-PKG` 一名两用（条件 ID 与门禁 ID 同名） —— 低

- **位置**：`§3.7` 第 189 行 与 `§7.1` 第 263 行
- **事实**：`§3.7` 的 `REL-PKG` 是 37 条之一；`§7.1` 的 `REL-PKG` 是 5 项门禁之一。其余 4 项门禁均为 `REL-VERIFY-*` 前缀，唯 `REL-PKG` 与底层条件同名。
- **为什么算问题**：`§7` 的标题是"5 项，不与 37 条重复计数"，而"REL-PKG"这个字符串确实同时出现在 37 里和 5 里。命名上无法自证未重复计数，只能靠读说明。
- **最小修订**：门禁侧改名为 `REL-VERIFY-PKG`（与其余 4 项前缀一致），或条件侧改名为 `C-PKG`。属纯命名，不动口径。

### F-08 `REL-VERIFY-PKGDIR` 与 REL-PKG 的 C 类是同一验收动作 —— 低

- **位置**：`§7.1` 第 264 行、`§3.7` 第 197 行、`§7.4` 第 280–281 行
- **事实**：P2-PKGDIR 已并入 REL-PKG 的 C 类验收，同时 `REL-VERIFY-PKGDIR` 作为门禁项保留，两者验收内容与通过标准**完全相同**（`app:runtime` 返回默认路径 + 目录树核对）。
- **为什么算问题**：`§7.4` 已声明"保留为 C 类标准 + REL-VERIFY-PKGDIR 视图"，所以**不构成重复计数**（这点已核实，不是错误）。但同一动作挂在两个门禁 ID 下、且没有指定哪一个是唯一判定源，将来分别登记状态时会出现"一处关闭、一处仍阻塞"或"两处都算关闭"。这是治理风险，不是算术错误。
- **最小修订**：`§7.1` 该行加"判定源 = REL-PKG 的 C 类；本行仅为只读视图，状态由 REL-PKG 派生，不得独立判定"。

## 5. 最终结论

### 5.1 台账是否一致

**实质口径一致，文档记法不一致。**

- 数字层面：37、3/2/1/31、2 硬阻塞 + 3 项发布前验证、去重规则、门禁与条件的"视图"关系——**全部成立且可复算**（三条独立算法同得 37，见 §1.1）。
- 记法层面：**11 处不一致**，其中 **F-01/F-01b/F-02/F-03/F-05/F-06 六项为中或高**，共同特征是"结论对、过程错"。最典型的是 F-01：40 这个"原始条目"实际是 43 减去 3 个未记录的归并，随后又用 3 个已记录的归并减到 37，两处错误相互抵消。
- 因此：**不构成口径层面的否定，但构成"台账自述的可复算性"不成立**。`§1.1` 的存在意义就是让外部复核者能重算，现在重算得 43 而不是 40。

### 5.2 是否需要修订

**需要，且应为一次轻量修订（v3）**：只改 `§1.1` 计算表、`§2` 表 A 的差額说明、`§3.2` 依据列、`§3.7` 来源清单、`§3.8` 计数、三处 `§4.3`、`§7.1` 命名与口径注，以及 C7-F5 的影响取值。

**明确不需要改的**：37 这个数、3/2/1/31 的分布、5 项门禁的等级划分（2 硬 + 3 必须）、任何条件的状态判定、任何"报告建议"的措辞。**修订不得升级或降级任何门禁，不得把"报告建议"改成"正式通过"。**

### 5.3 下一步最优先处理什么

**第一优先：完成 v3 轻量修订（仅文档，不改任何判定）。**
理由：台账已是全项目的判定基线，后续所有发布决策、所有"哪些能推迟"的讨论都以它为据。它的结论对、账目错——这恰恰是最危险的状态：一个算不出 37 的台账，会在第一次外部复核时被整体质疑，连带把本来站得住的 37 一起否掉。修订成本是文档级的，代价远低于"结论被连带否定"。

**第二优先：解除两个硬阻塞（顺序不可换）。**
1. **REL-ICON**：提供 `build/icon.ico`（多尺寸，16–256）。这是唯一不需要任何运行就能解掉的阻塞项，且 `electron-builder.yml` 已指向该路径，缺文件时 `dist:win` 本身就跑不起来。**它是 REL-PKG 的前置条件。**
2. **REL-PKG**：执行 `dist:win` + 安装/升级/卸载 + 打包后目录隔离 + asar worker 295-jar 冒烟（含审计 C3）。四类验收缺一不可，任一失败须留原始错误证据，尤其 D 类要盯 `ERR_WORKER_PATH`。

**可以并行、但不阻塞发布的三项验证**：REL-VERIFY-PKGDIR（打包后目录）、REL-VERIFY-DUAL（安装版 + dev 并行）、REL-VERIFY-4K（4K 截图）。其中 4K 是否升格硬门禁仍需负责人裁定（`§8` #2）；`§8` 全部 7 项待决策事项中，只有 #3（C3 归属，影响 37 vs 38）会动总数，其余均不动。
