### 2.3 原子性设计（核心）

难点：C-6/C-7 是**多文件**，中途失败会留下"混合世代"。设计分三层：

**第 0 层 · 前置校验（不写任何源码）**
1. 对 5/10 个备份文件逐一 `sha256sum`，与 §2.2 表比对；任一不符 → **中止**。
2. 对每个目标文件检查"是否可写"（`fs.accessSync(W_OK)`）；任一不可写 → **中止**。
3. 确认 `.cache` 与 `src` **同盘**（`rename` 才能原子）：`fs.statSync` 的 `dev` 相同 → 否则改用 copy+校验。

**第 1 层 · 快照（演练前的唯一真相）**
4. 建 `.cache/fix12-drill/<group>-<ts>/{src,tests}/…`，把**每个将被动到的当前文件**按原相对路径复制进去；
5. 生成 `manifest.json`：`{ path, preHash, backupHash, needReplace }`；
6. **回读校验**：快照内每个文件的哈希必须等于「当前哈希」→ 任一不符 **中止**（此时源码尚未动）。

**第 2 层 · 换入 / 还原都走"暂存 + rename"**
7. 换入：先把备份文件复制到 `.cache/fix12-drill/stage-<group>/`（同盘）→ 校验暂存副本哈希 == 备份哈希 → 再对每个目标 `rename(stage, target)`（同盘 rename 原子，且要么成功要么原文件仍在）；
8. 还原：用快照做同样的事（复制到 stage → 校验 → rename）；
9. 每次 rename 后立刻 `sha256sum` 复核；**任何一步不符 → 进入"紧急还原"**：用快照的 stage 重放一遍 rename，并再复核一次。

**第 3 层 · 兜底（脚本失效时的人工路径）**
10. `manifest.json` 足以让人工逐个 `cp` 还原；报告里给出**逐条命令**。

> **诚实说明**：第 2 层仍然不是"真事务"——若在 rename 循环中途进程被杀，会留下部分新、部分旧的混合状态。
> 缓解：文件数少（5 / 8 个有效项）、逐个 rename 间隔毫秒级、且 restore 也是一条固定命令序列。
> **若负责人要求"任何中断都能自动回滚"，则本方案不满足**，需要先引入"影子目录 + 目录级切换"（改动构建/运行结构，超出本批授权）。
