## 2. 问题 1：43 的追溯诊断

### 2.1 43 的构成

上一份报告的表格实际是：

| 组 | 条目数 |
| --- | --- |
| P-C7 §9（F1–F7） | 7 |
| P-OPT4-最终验收 §4（风险 1–8）+ §5（C1 约束句） | 8 + 1 = 9 |
| UI §10（U1–U6） | 6 |
| P0 §9（1–3）+ §10（R1–R3） | 6 |
| P1 §六 未完成（1–5） | 5 |
| P2 §11（1–3）+ 审查 §7.2（5 项）+ 审查 §7.7-1 | 9 |
| **来源小计** | **42** |
| ＋ "合成项 REL-PKG" 行 | **+1** |
| **表内合计** | **43** |

**用户的加法是对的：六个来源组之和为 42。** 43 之所以出现，只因表里多了一行"合成项 REL-PKG 1"。

### 2.2 为什么 +1 不成立

REL-PKG 不是任何报告里的条目，它是**三条来源合并后的产物**：

- `P2` §11-1「正式安装版未实测」
- `UI` §10 U6「打包产物 `dist:win` 未验」
- `P1` §六-2「未打包 / 未做安装与卸载测试」

这三条已经**在 42 里面**。因此：

- 若把 REL-PKG 当来源再加 1 → 同一件事被算两次（三条来源 + 它们的合并结果）；
- 为了让总数回到 37，必须把三条来源逐条减掉（−3）；
- 于是"三条变一条"的净效果 −2，被记成 "+1 与 −3" 两笔。

**两笔相加仍等于 −2，所以 37 没算错；错的是把它写进"原始条目"表。** 一张标称"原始条目"的表里不允许出现归并产物。

### 2.3 顺带发现：C1 也不是"风险条目"

`P-OPT4-最终验收` §4 只有 8 条编号风险（1–8），**§5 验收结论中没有任何编号条目 C1**。台账的 `OPT4-C1` 实际取自 §5 结论第二句："封板后除缺陷修复外，不再改动 P-OPT 涉及的扫描/写入/zip 路径"——这是一句**约束**，不是风险条目。

按 R1，C1 本不该进候选池。台账"先纳入再移出（−1）"在算术上是空转，但对读者是误导：它让人以为 OPT4 有 9 个条目。**更准确的写法是：OPT4 候选 8 条，C1 单独作为"执行约束"登记，不参与任何加减。**

## 3. 问题 2：42 → 37 的完整算式

推荐采用**六步显式算式**（每一步只做一件事，且 +1 与 −3 都可见）：

| 步骤 | 动作 | 数量 | 依据 |
| --- | --- | --- | --- |
| ① | 已登记来源条目合计（六组之和） | **42** | 见 §2.1 表 |
| ② | `OPT4-R1`（仅 Windows 验证）并入 `C7-F2`（跨平台验证父条件） | −1 → **41** | `P-OPT4` §4 第 1 条；`P-C7` §9 F2 |
| ③ | `OPT4-R5`（90s 未证明稳定）并入 `C7-F3`（冷启动 ≤90s） | −1 → **40** | `P-OPT4` §4 第 5 条；`P-C7` §9 F3 |
| ④ | `OPT4-C1` 判定为执行约束，移出条件表 | −1 → **39** | `P-OPT4` §5 结论第 2 句（非条目） |
| ⑤ | 打包三源（`P2`§11-1 / `UI`U6 / `P1`§六-2）合并为一条 | −3 → **36** | 同一根因：未打包、未验安装链路 |
| ⑥ | 新增合成条件 `REL-PKG`（承接上述三源 + **审计 C3** 的 asar worker 冒烟） | +1 → **37** | `P1` §六.2；`P2` §11.1；`PROJECT-WIDE-AUDIT` §9-C3 |

**校验：42 − 1 − 1 − 1 − 3 + 1 = 37** ✓

### 3.1 为什么第⑥步必须单独列出

若按"三条变一条，净 −2"写成 `42 − 5 = 37`，算式更短，但会**丢掉一个关键事实**：REL-PKG 并非纯粹的三源合并，它还**新增了审计 C3 的要求**（打包环境下 `new Worker(__dirname/scan.worker.js)` 能否运行 + 295-jar 冒烟）。

- 三源只要求"打包并安装验证"；
- C3 要求"asar 内 worker 可运行"，这是一条**在阶段报告中从未出现**的新验收项。

所以 REL-PKG 的净增不是 0，而是"吸收 3 条 + 新增 1 条要求"。写成 −3/+1 两步，才能让 C3 的引入可见，也才对得上裁决报告 §2.3"C3 作为 REL-PKG 的 D 类验收"。

### 3.2 与另两条算法的交叉校验

| 算法 | 算式 | 结果 |
| --- | --- | --- |
| 状态分布 | 3（已解决：C7-F5、UI-U1、P1-DEVPROD）+ 2（部分：C7-F3、P1-GUARD）+ 1（待验证：P2-DUALFORM）+ 31（未解决） | **37** ✓ |
| 分组累加 | C7 7 + OPT4 6 + UI 5 + P0 6 + P1 4 + P2 8 + REL-PKG 1 | **37** ✓ |
| 归并算式 | 42 − 1 − 1 − 1 − 3 + 1 | **37** ✓ |

三条算法互不依赖，均得 37。**这是 37 成立的最强证据**——归并算式即使写错，另两条也不受影响。
