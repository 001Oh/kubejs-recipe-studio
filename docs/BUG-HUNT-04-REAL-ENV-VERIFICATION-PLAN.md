## 1. 总体验证策略

### 1.1 三层证据分级（沿用 BUG-HUNT-02/03 口径）

| 层 | 含义 | 当前状态 |
| --- | --- | --- |
| **① 代码已修改** | 源码里有对应改动 | 多数项已完成 |
| **② 测试通过** | 自动化测试在 `node` 环境跑过 | BUG-HUNT-03 结束：79 文件 / 742 用例 / 0 失败 |
| **③ 真实环境已验证** | 启动应用 + 真实整合包 + 真实交互 | **0 项** |

本计划的**唯一目标**是把可验证项从 ② 推进到 ③，并**明确哪些项永远无法在本机推到 ③**。

### 1.2 划分原则

- **只验证"自动化测试无法覆盖的差异"**：能靠单测证明的逻辑（如 `augment` 去重、`applyMerge` 幂等）不再重复做真机测试。
- **优先选"可观测且可回滚"的信号**：每个 RT 都要有能在界面上/日志里**一眼看出来**的判据，而不是靠"感觉正常"。
- **包级差异优先用"内嵌插件"制造**：`<整合包>/.recipe-studio/plugins/` 是**包作用域**的，比"删模组"更精准、更容易回滚（见 §1.3）。
- **不假定能力**：所有隔离手段都先在源码里核实过（§2），未核实的一律列阻塞。

### 1.3 关键设计决策：用「包内嵌插件」制造 A/B 差异

本轮核实：`ensureSchemas()` 的 `builtin` 层只装 **3 个试点 schema**（`PILOT_SCHEMAS`），`plugin` 层来自插件（含**包内嵌**插件目录），`pinned` 来自 userData。
因此"换包"能改变的实际是：`factsKey`（路径/记录数/类型数/附属数/模组数）+ **包内嵌插件集合**。

> 若只在两包间删减模组 jar，`capability` 可能**完全不变**（三个试点类型的判定对 `installedModIds` 不敏感：
> `minecraft:*` 的 `ns` 恒为已安装；`create:mixing` 在两包中都是 `unsupported`）。**这样的 A/B 无法证明 REM-01 是否修好。**
> 所以 RT-01/RT-02 统一用「A 包内嵌一个声明 `rt04a:only` 的插件，B 包没有」作为差异源——它直接改变 `plugin` 层，可观测、可回滚。

**R1 补充核实（推翻了原方案对观测点的两个假设）**：

1. **注册表实际只有三层内容**。`service.ensureSchemas()` 只装配 `builtin`（= `PILOT_SCHEMAS` 的 **3 个**试点类型）、
   `plugin`（provider）、`pinned`（userData）三层；`jar` / `inferred` 两个层在 `src/main` 中**没有任何填充调用方**
   （全仓 `putMany(` 唯一调用点是 `service.ts:136`）。→ **注册表里的类型集合 = 3 试点类型 ∪ 插件声明类型 ∪ 钉住类型**。
2. **因此 `create:mixing` 很可能根本不在注册表里**（pc7 包内无 create jar；无插件声明；不是试点类型）。
   原 RT-01 用 `create:mixing` 做观测点，实际只会得到"未找到配方类型 schema"，**与新鲜度无关**。
   R1 已把它降级为**阴性对照**（见 §2.4 与 RT-01），不再作为"旧插件 Schema 已清除"的证据。

> **结论**：能同时满足「A 有 / B 无」且「预览可直达」的观测点**只有插件声明类型本身**（`rt04a:only`）。
> 这是 R1 修订 RT-01 的全部依据。

### 3.2 生产数据零影响：授权分层与能证明的边界（R1 重写）

原 §3.2 直接要求"执行前后对生产 userData 做清单 + 总哈希比对"。这条写法有两个问题：
① 把"读取生产 userData"当成了默认动作；② 把"前后哈希一致"夸大成"证明期间从未写入"。
R1 改为**四段分离**：隔离验证 → 访问授权 → 完整性核对 → 能证明/不能证明。

#### 3.2.1 隔离验证（默认路径，**不需要任何生产数据权限**）

| 步 | 动作 | 通过条件 | 失败即停止 |
| --- | --- | --- | --- |
| I1 | 只设 `STUDIO_USER_DATA` 为**绝对路径**（如 `E:/_rt04/ud-01`） | 值为绝对路径且位于 `E:/_rt04` 下 | 含相对段、含 `..`、落在 `%APPDATA%` |
| I2 | **不传** `--user-data-dir` | 启动命令行无该参数 | 出现该参数 → 放弃本次执行（§2.3 R2） |
| I3 | 启动后从**日志**确认实际数据目录 | 日志首部出现 `数据目录（env）: E:/_rt04/ud-01`，来源标记为 `env` | 日志缺该行；来源不是 `env`；路径不含 `_rt04` |
| I4 | 在 I3 通过**之前**不做任何写用户数据的操作（导入包／pin／改插件／开关插件） | 无写入发生 | 已写入 → 停止并按 §3.3 处置 |
| I5 | 每个实例用**不同**的 `STUDIO_USER_DATA` | 并行实例目录互不相同 | 复用同一目录（单实例锁互踢，见 R3） |

> I3 是**唯一的隔离成功判据**。`-dev` 后缀、进程参数、猜测的默认路径都**不算**证据。
> 日志不可读或来源标记缺失时按"隔离未确认"处理，**不得**先跑测试再补证。

#### 3.2.2 生产 userData 访问授权（独立事项，默认**未授权**）

| 项 | 规则 |
| --- | --- |
| 默认状态 | **不访问、不列举、不算哈希、不比较修改时间**。R1 修订轮亦未访问（见 §11） |
| 需要时的授权形态 | 由用户**单独明确授权**"只读列出 `<具体绝对路径>` 的文件数／字节数／最大 mtime"；授权只对点名的路径与指标有效 |
| 不被视为已授权的动作 | 读取目录内容、递归 `find`、`Get-ChildItem -Recurse`、对内容算哈希、把清单写入 `E:/_rt04/backup/` |
| 授权前的替代手段 | 只依赖 §3.2.1；隔离成立即视作"生产未被写入"的**充分工程条件** |
| 授权后的记录要求 | 授权范围、执行人、时间、命令原文、输出路径写入 `evidence/`；**不得只写结论** |

#### 3.2.3 完整性核对（仅当 §3.2.2 授权后才存在）

- 采样口径必须**固定可复算**：同路径、同命令、同排序（如"相对路径 + 字节数 + 最后写入时间"逐行排序后整体哈希）。
- 必须**逐行 diff**，不得只比总哈希（总哈希相同不能排除"同时增删"）。
- 出现任一行差异 → **停止该批次**，先判定是"应用写入"还是"系统/杀软触碰"（如 `desktop.ini`、索引服务），
  判定依据必须记录，**不得直接归因为缺陷**。

#### 3.2.4 这套方法能证明什么、不能证明什么

| 能证明 | 不能证明 |
| --- | --- |
| 隔离实例的**实际**数据目录是 `E:/_rt04/ud-0x`（日志实证） | 隔离实例"绝对没有"碰过生产目录的**其它**资产（注册表、快捷方式、`%LOCALAPPDATA%` 缓存） |
| I3 通过后，应用的读写都落在隔离目录（应用层证据） | 操作系统层面（杀软、索引、备份代理）是否访问过生产目录 |

> 当作已证明。据 §2.4 F11，`getCorpus()` 的重建**无日志、无计数器**，`indexPathBuiltAt()` 未暴露且不被惰性重建更新；
> 据 F10，查询返回的 `elapsedMs` **不含**重建耗时。→ "重建次数"当前**没有直接证据通道**。
> R1 因此把验收拆成 A（功能正确性，可判通过）与 B（性能与重建行为，只能记录观测值），**禁止合并成一个总结果**。

### 7.1 各 Q 项的技术事实、备选与风险（**均为待裁决**）

#### Q-01 · pinned Schema 是否跨包保留

| 项 | 内容 |
| --- | --- |
| 当前实现 | `customRecipeTypes.json` 位于 **userData 根**（不在包目录），`ensureSchemas()` 每次重建都会 `loadPinned()`；`pinned` 是**最高优先级层** |
| 可观测后果 | 换包后旧包钉住的类型**仍在列表里**，且优先级高于新包的 `plugin`/`builtin` |

| 备选 | 做法 | 风险 |
| --- | --- | --- |
| A（现状） | 全局保留 | 旧包类型遮蔽新包定义；用户难判断"这个类型为什么还在" |
| B | 按包隔离（`customRecipeTypes/<包 hash>.json`） | 用户换包后需重新钉住；改变"全局偏好"的既有预期；需迁移旧文件 |
| C | 保留但标记"来自其它包" | 需要新的 UI 状态与判定口径，工作量大 |

> **待裁决**：三者均需产品决定。**本轮不选**。

#### Q-02 · 插件目录不可读时的语义（**必须四分，不得合并**）

| 情况 | 触发方式 | 当前代码路径的结果 | 是否合理 |
| --- | --- | --- | --- |
| ① 目录正常且为空 | 无任何插件文件 | `readdir` 成功返回 `[]` → 插件层为空 | **合理**（确实没装插件） |
| ② 目录不存在 | 删除整个插件目录 | `readdir` 抛 `ENOENT` → 被 catch → `[]` → 层为空 | **待定**（"没装插件"与"目录被误删"产品语义是否等同） |
| ③ 目录存在但读取失败 | ACL 拒绝／占用／IO 错误（RT-05 S2 的做法：改名或改权限） | 同样被 catch → `[]` → **层被清空** | **可疑**——用户没删插件，但所有插件类型消失 |
| ④ provider 本身抛异常 | 需注入点，真实环境无法构造 | `fetchLayer` 返回 `{ok:false}` → `ensureSchemas` 恢复 `snapshotLayer('plugin')` → **保留旧层** | 已由 RV1-003 处理 |

> **关键提醒**：①②③ 最终都产生"空数组"，但**不能因此认定三者语义相同**——②③ 是"读不到"，① 是"确实没有"。
> 这正是 ④ 已经被区别对待、而 ②③ 没有的原因。

| 备选 | 内容 | 风险 |
| --- | --- | --- |
| A | **保留旧层**（与 ④ 一致：任何失败都不清层） | "真的删了插件"时若读目录仍失败，旧类型会持续存在，用户以为没删掉 |
| B | **清空视为无插件**（现状） | 权限/占用等临时故障会表现为"插件全部消失"；此时若用户 pin 了某个类型，可能把错误状态固化到 `customRecipeTypes.json` |
| C | **区分对待**：①②→空层；③→保留旧层 + WARN；④→保留旧层 | 需要区分 `ENOENT` 与其它错误码，属产品语义 + 代码改动 |
| **待裁决** | 三选一（或另定）。**本轮不选**，RT-05 S2 在其裁决前**不得判通过或失败** | — |

#### Q-03 · A/B 包无可观察差异时

- **技术事实**：`factsKey()` 含包路径（`service.ts:109`），A/B 是不同目录 → 换包后 `ensureSchemas()` **必然**重建。
  但"必然重建"只说明机制被触发，**不说明内容层面有可见差异**。若两包在插件层/钉住层上完全一致，界面观测不到任何变化。
- **明确结论**：**没有可观察差异时，不得宣称"已验证旧状态正确更新"**——因为无法区分"已更新"与"本来就没变"。
- 可选处置：① 记为"环境不具备，无法验证"；② 换更强的差异源（需改包内容，属 §7 Q-06 范畴）。
- **待裁决**：是否接受"无法验证"作为该情形下的正式结论。

#### Q-04 · 语料重建是否需要可观测计数

| 项 | 内容 |
| --- | --- |
| 现有证据 | 查询结果正确性、`total` 稳定、`elapsedMs` 同量级（但 `elapsedMs` **不含**重建） |
| **不能**证明 | 重建**发生次数**；"只在规则变化时重建一次"；重建耗时 |
| 原因 | `getCorpus()` 重建无日志/无计数器（§2.4 F11） |
| 选项 A | 接受现状 → RT-04 B 类永远记为"未直接验证" |
| 选项 B | 加一行 debug 日志（**代码改动**）→ 可计数，需单独授权 |
| 选项 C | 暴露一个只读计数 IPC（**代码改动 + 契约变更**）→ 可计数，成本更高 |
| **待裁决** | 是否值得为该项引入代码改动 |

#### Q-05 · 性能验收阈值

- 原计划里的"慢 5 倍以上""超过 `corpusMs` 3 倍"是**撰写时的暂定实验告警阈值**，**从未获得产品验收授权**。
- **R1 明确**：这些数字**不得**写成产品要求，也**不得**作为 RT-08 的通过/失败线；只能作为"是否需要进一步分析"的触发器。
- 可选项：① 由产品给出预算；② 先只做基线测量、不设阈值；③ 用"同机同包、改前改后对比"的相对口径（但仍需产品确认可比性）。
- **待裁决**：由谁定、定多少。

#### Q-06 · 是否允许在包副本中新增测试数据

- **事实**：RT-01／RT-02／RT-03 的全部测试数据都是**人为构造**的——内嵌插件 JSON（§A.1）、`kubejs/data/rt04a/recipes/probe.json`、
  把 `minecraft:stone` 标为虚拟的测试插件。**它们都不是原整合包自带内容。**
- **R1 要求**：所有结论必须写明"在**修改过的包副本**上验证"，**不得**表述为"在真实整合包上验证通过"。
- 可选项：① 接受（只改副本，可 `cp -r` 回滚）；② 要求改用带真实插件的包（当前**无此样本**）。
- **待裁决**：是否接受人为构造的测试数据作为 ③ 类证据。

#### Q-07 · 同 size、同 mtime 的插件热更新

| 项 | 内容 |
| --- | --- |
| 当前签名 | 路径 + mtime + size（BH-014 引入） |
| **能**捕获 | 内容变化且 size 或 mtime 变化 |
| **不能**捕获 | size 与 mtime 都不变而内容变了（例如用工具把 mtime 改回原值、且新旧内容等长） |
| 选项 A | **接受现有限制**，在文档与 UI 提示中记为已知局限 |
| 选项 B | 改用内容哈希（每次加载全量读文件 + 哈希）→ 能覆盖，代价是加载变慢、插件多时明显 |
| 选项 C | 双轨：先比 mtime+size，命中后再比内容哈希（成本居中，实现更复杂） |
| **待裁决** | **不得**擅自决定"产品必须支持"或"无需支持" |

## 9. 每项验证的通过标准（汇总）

### 9.1 四种状态的定义（R1 新增，**每个 RT 必须落到其中一个**）

| 状态 | 定义 | 允许的写法 | 禁止的写法 |
| --- | --- | --- | --- |
| **通过** | 该 RT 的**全部**通过判据都满足，且证据可复核（截图/日志/返回值） | "RT-0x 通过：判据 1/2/3 均满足，证据见 `evidence/RT-0x/`" | 省略判据直接写"通过" |
| **部分验证** | 部分判据满足、部分因观测通道缺失而无法判定（例如 RT-04 的 B 类） | "功能行为通过（A 类 4 项）；重建次数未直接验证" | "部分通过"这种含糊说法 |
| **无法验证** | 关键前置不成立，测了也不指向结论（例如 RT-02 情况 A） | "无法验证：B 中配方不可达，无证据指向 schema 路径" | 把"环境搭不起来"写成"通过" |
| **未执行** | 本轮/本批次没做 | "未执行（原因）" | 留空或写"待补" |

> **铁律**：**任何无法直接验证的项目必须保留明确状态，不得自动转为通过**；
> 也不得为了让"看起来都做完"而放宽判据。

### 9.2 逐项通过标准

| RT | 通过 = 全部满足 |
| --- | --- |
