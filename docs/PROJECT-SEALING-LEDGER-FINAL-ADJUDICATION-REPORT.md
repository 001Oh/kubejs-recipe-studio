## 3. B 项：C7-F2 与 OPT4-R1 合并裁决

| 项 | 原文 | 对象 | 验收动作 |
| --- | --- | --- | --- |
| C7-F2 | `P-C7` §9：「跨平台文件系统验证（Linux/macOS：rename、权限、行分隔）」 | **提交/备份链路的文件系统语义**（rename 覆盖、只读权限、行分隔） | 在 Linux/macOS 上跑提交覆盖、回滚、只读失败用例 |
| OPT4-R1 | `P-OPT4` §4.1：「仅 Windows 验证：`rename` 作为句柄释放证据依赖 Windows 占用语义；POSIX 未验证」 | **ZIP 读取 API 的句柄释放证据**（rename 只是判定手段）与 listAndRead 语义 | 在 POSIX 上跑 `listAndRead` 句柄释放/并发/内容一致性用例 |

**裁决：属于「同一根本问题（只验证了 Windows），两个不同验收目标」→ 允许合并为父条件，但不得取消任一验收动作。**

- 合并成立的条件：父条件描述必须写成「跨平台验证（提交/备份文件系统语义 + listAndRead/zip 语义）」。
- 若只保留「跨平台验证」五个字，则**丢失 R1 的验收动作**，此时应保留两条。
- 建议表述：`C7-F2 跨平台验证`（父），子项 `C7-F2a`（提交/备份）、`C7-F2b`（listAndRead/zip）。

## 10. 最终结论

**必须回答的六个问题：**

1. **37 条是否成立？**
   **成立**——但以两个前提为条件：REL-PKG 吸收 C3 冒烟、C7-F2 保留两个子验收。否则应为 38 或 39。算术不是依据，逐条原文核对与去重规则才是。

2. **C7-F2 与 OPT4-R1 是否应合并？**
   **应合并**（同一根因：只验证 Windows），但**不得取消任一验收动作**；合并后父条件须含「提交/备份文件系统语义」与「listAndRead/zip 语义」两个子项。

3. **4K 复验属于哪种发布要求？**
   **发布前必须完成的验证**。依据 `UI` §11「前置条件…发布前补一次 dist:win 与 4K 视口复验」。原文没有「未完成不得发布」措辞，故不判为硬性门禁；是否升格需负责人确认。

4. **打包、安装、目录隔离和双形态并行是否都被完整覆盖？**
   **原总账不完整**：目录隔离与双形态被折叠进 REL-PKG、4K 缺位、C3（asar worker）完全缺失。按本报告 §5 的 5 项拆分后**才完整覆盖**；当前这 5 项状态均为「未解决/未验证」。

5. **原总账是否可以进入修订阶段？**
   **可以**。修订清单见 §9（9 处）。修订属于文档工作，不涉及代码，但需负责人授权后执行。

6. **在实际打包及相关验证完成前，项目是否仍应保持「尚未达到正式发布条件」？**
   **是。** 依据：`build/icon.ico` 不存在、从未执行 `dist:win`、无安装/升级/卸载记录、打包后目录与双形态未验证、4K 未复验、asar worker 未验证。

**一句话裁决**：条件是 37 条（附两前提），合并成立但不取消验收，4K 属发布前必须完成的验证，发布门禁必须由「2 硬阻塞 + 3 验证项」共同构成；**在打包与验证完成前，项目不具备正式发布条件**。
