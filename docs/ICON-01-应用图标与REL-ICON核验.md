## 3. 小尺寸辨识度方案（本轮最关键的决定）

初版实现采用"等比缩放 + 小尺寸自动加粗描边"，在 16/24px 上**失败**：描边 1.9px、间距 0.6px，3×3 单元格的边框互相粘连，16px 退化成一块青色糊团（已留档，见 `.cache/icon-gen/preview/` 首轮对照）。

原因是算得清的：16×16 要容纳 3 个单元格 + 2 条间距 + 6 条描边边，若描边取 1.9px 则 3×(1.9+interior+1.9) 早已超出 16px 预算。**这是几何约束，不是调色问题。**

因此改为**光学尺寸变体**（而非同一图形硬缩放）：

| 尺寸 | 变体 | 具体做法 |
| --- | --- | --- |
| 16 / 20 / 24 | **格线变体** | 不画单元格，画 2 竖 + 2 横的 1px 青绿格线（"#"），读作 3×3 网格；齿轮放大 1.20× |
| 32 | 单元格变体（简化） | 3×3 圆角单元格，描边压到 1.15px 像素下限，间距 ≥1.05px；齿轮 1.10× |
| 48 / 64 | 单元格变体（中） | 加顶部内阴影与齿轮投影 |
| 128 / 256 / 1024 | 完整版 | 加外发光、面板高光、齿轮轮缘 |

同时把**描边与间距改成像素下限**（`max(0.016, 1.15/size)`、`max(0.028, 1.05/size)`），杜绝亚像素合并。

> 这是一次有意的"跨尺寸不一致"：同一 App 在 16px 与 256px 下不是同一张图的缩放，而是同一套视觉语言的两个光学字号。Windows 商店应用与 VS Code 等桌面工具普遍采用该做法。

## 4. ICO 二进制校验（独立解析器，不复用生成代码）

工具：`.cache/icon-gen/verify_ico.py`（按 ICO 规范逐字段解析，非调用生成器）

```
文件：build/icon.ico（84,238 字节）
ICONDIR: reserved=0 type=1 count=8
宽      高        bpp   字节      格式
16      16       32    1128      BMP
20      20       32    1720      BMP
24      24       32    2440      BMP
32      32       32    4264      BMP
48      48       32    9640      BMP
64      64       32    16936     BMP
128     128      32    13907     PNG
256     256      32    34069     PNG
尾部对齐：目录+数据 84238 / 文件 84238 → 一致
尺寸集合：[16, 20, 24, 32, 48, 64, 128, 256]
结论：全部通过
```

**透明通道检查**

- 8 个条目**全部**存在 `alpha < 255` 的像素（圆角与 4.5% 边距），不存在"全不透明矩形"问题。
- BMP 条目的 alpha 由逐像素 BGRA 写入（非全 0），AND 掩码全 0（由 alpha 主导）——这是 Windows 下最稳的组合；若 alpha 全 0 会得到"图标不可见"的经典故障，本次已排除。
- 主图 `build/icon.png` 为 `RGBA 1024×1024`，角像素 `alpha=0`。

**为什么 BMP 与 PNG 混用**：≤64px 用 DIB 兼容性最好（老版资源管理器、NSIS 安装器、部分第三方工具只认 DIB）；128/256 用 PNG 可把文件从约 300 KB 压到 34 KB，且 256 PNG 是 Vista 以后的通行做法。

## 5. `electron-builder.yml` 配置核验

配置现状（未修改）：

```yaml
directories:
  buildResources: build
win:
  target: [nsis]
  icon: build/icon.ico
```

**实际解析路径**（读 `node_modules/app-builder-lib/out/platformPackager.js:502-524`，electron-builder **25.1.8**）：

1. 若 `custom` 是资源目录内的**裸文件名** → 返回 `buildResources/custom`；`build/icon.ico` 不是裸名，不走此分支。
2. 若 `buildResources/custom` 存在 → 即 `build/build/icon.ico`：**不存在**。
3. 否则回退 `projectDir/custom` → `E:/mc kjs/build/icon.ico`：**存在 ✅**。
4. 都不存在才抛 `cannot find specified resource`。

**结论**：当前写法**可正确解析**（走第 3 步回退），不会报"找不到图标"。

**一处可优化但本轮不改**：因 `buildResources` 已是 `build`，更直接的写法是 `icon: icon.ico`（命中第 1 步，不再依赖回退）。本轮按"不做无关改动"保留原写法；两者行为等价，待打包实测确认无告警后再决定是否顺手规范。

## 6. REL-ICON 为什么现在还不能关闭

台账 V3 中 `REL-ICON` 的关闭条件是：**"多尺寸 ICO；打包无告警"**（§9 行动清单第 1 项）。

| 关闭条件 | 当前证据 |
| --- | --- |
| 多尺寸 ICO | ✅ 8 尺寸，二进制校验通过（§4） |
| 打包无告警 | ❌ **尚未执行打包**，无 `dist:win` 日志 |

按执行纪律"只有实际验证通过并留存证据后，才能关闭对应台账条件"，本轮**不关闭 REL-ICON**，也不修改主台账。它将在下一阶段 `dist:win` 成功后，依据"命令 / 退出码 / 是否出现 icon 相关 warning"三条证据关闭。
