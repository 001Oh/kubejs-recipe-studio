# 一、项目背景（必须先理解，否则架构会错）

KubeJS 是 Minecraft 的脚本模组，服务端脚本放在整合包目录下的 `kubejs/server_scripts/*.js`，格式如下：

```js
ServerEvents.recipes(event => {
  // 原版有序合成
  event.shaped('4x minecraft:oak_planks', [
    'A',
    'A'
  ], { A: 'minecraft:oak_log' })

  // 原版无序合成
  event.shapeless('minecraft:stick', ['minecraft:oak_planks', 'minecraft:oak_planks'])

  // 模组配方（Create 搅拌）
  event.recipes.create.mixing(
    Fluid.of('minecraft:water', 500),
    ['minecraft:dirt', 'minecraft:sand']
  ).heated()

  // 移除配方
  event.remove({ id: 'minecraft:diamond_sword' })

  // 任意模组的兜底写法（原生 JSON 配方格式）
  event.custom({
    type: 'thermal:pulverizer',
    ingredient: { item: 'minecraft:cobblestone' },
    result: [{ item: 'minecraft:gravel', count: 1 }],
    energy: 4000
  })
})
```

**关键事实**（直接决定架构）：

1. `event.custom({ type: '...' })` 接受**任何**模组的数据驱动配方 JSON，只要该模组注册了 `RecipeType`。这是"支持所有模组"的终极兜底通道。
2. `event.recipes.<modid>.<method>(...)` 是 KubeJS 为部分模组提供的语法糖，**并非所有模组都有**，且方法签名不统一。
3. KubeJS 语法在版本间有破坏性变更：MC ≤1.18 用 `onEvent('recipes', e => {})`；MC ≥1.19 用 `ServerEvents.recipes(e => {})`。程序必须按检测到的版本生成对应头部。
4. 物品 ID 与本地化名不可从「已安装模组列表」推断，必须解析 mod jar 内部资源。

## 3.2 数据构建（物品索引 A/B + 配方数据库 C）

### 源 A：解析 `mods/*.jar` — 物品索引（默认，离线可用）

对每个 jar 流式解压并只读取以下条目（**不要全量解压到磁盘**，用内存流）：

```
assets/<ns>/lang/zh_cn.json
assets/<ns>/lang/en_us.json
assets/<ns>/lang/*.json   (其余语言作补充)
assets/<ns>/models/item/*.json
assets/<ns>/textures/item/*.png
assets/<ns>/textures/block/*.png
```

**物品 ID 提取（按置信度分层，求并集）**：

1. **最高置信**：lang 文件的键 `item.<ns>.<path>` → 物品 `ns:path`
2. **高**：`block.<ns>.<path>` → 方块物品 `ns:path`（多数方块有对应物品）
3. **中**：`models/item/<path>.json` 存在 → 推断 `ns:path`
4. **低**：`textures/item/<path>.png` 存在 → 推断 `ns:path`
5. 排除：`path` 含 `_spawn_egg` 以外的 `debug_`、`_overlay`、`_layer` 等明显非物品资源；排除 lang 键中的 `itemGroup.`、`item.mod.*`、`item.kubejs.*` 等非物品条目

**名称解析**：`zh_cn.json` 优先，缺项回退 `en_us.json`，均缺则用 ID 的 `path` 部分转可读形式。同时保留英文名用于搜索。

**图标提取（侧边栏的核心视觉，必须做扎实）**：

- 优先 `textures/item/<path>.png`
- 次选 `textures/block/<path>.png`
- 再次：读 `models/item/<path>.json` 的 `textures.layer0` / `textures.all`，解析出实际贴图路径（可能是 `ns:item/xxx` 形式，需要再拼 `assets/<ns>/textures/<...>.png`），最多跟两层
- 还要处理 `parent` 继承：模型 JSON 可能只声明 `"parent": "item/generated"` 而贴图在父模型里，需沿 `parent` 链向上查找（最多 3 层）
- 全部失败 → 前端渲染占位图（深色块 + 名称首字）

> **占位图是异常兜底，不是常规显示方式。** 正常路径下侧边栏、槽位、配方卡片里显示的都必须是真实的 16×16 物品贴图。若发现大量物品落到占位图，说明图标提取逻辑有问题（常见原因：没处理 `parent` 继承、没拼对 `textures/` 前缀），应当修提取器而不是接受占位。

图标以 16×16 原尺寸 PNG 提取，存 `userData/icon-cache/<sha1(id)>.png`，前端通过自定义协议 `app-icon://<sha1>` 加载。界面渲染必须 `image-rendering: pixelated`，禁止平滑缩放。

**性能要求**：300+ mod 的整合包首次扫描 ≤ 90 秒，必须显示进度（`正在解析 128/412：create-1.20.1.jar`）。扫描在主进程用 worker_threads 并行（并发数 = `os.cpus().length`，上限 8），主线程不阻塞。结果写入 `userData/cache/<modpackPathHash>/items.json`，二次启动 < 2 秒直接命中缓存。缓存通过「mods 目录 mtime + jar 数量 + 总大小」做失效判断。

### 源 B：ProbeJS / CraftTweaker 注册表导出导入（可选，高置信）

提供「导入注册表导出」按钮，接受以下任一：

- **ProbeJS**：`kubejs/probe/` 下的 `*.d.ts`（递归）。解析策略：宽松正则扫描 `"[a-z0-9_.-]+:[a-z0-9_./-]+"` 形式的字符串字面量，结合所在 `interface`/`namespace` 名判断是否属于 Item/Block/Fluid 注册表。不要求完整解析 TypeScript。
- **CraftTweaker `/ct dump items`**：`scripts/` 或 `dumps/` 下的 `.txt`，每行一个 ID。
- **EMI `/emi dump registry`** 或 **KubeJS 导出**：`.json`，递归遍历找形如 `namespace:id` 的字符串字段。

导入后与源 A 结果**合并**：相同的 ID 提升置信度并标记 `verified: true`，界面在已注册物品上显示小对勾。源 B 独有但源 A 没有的 ID 也要收录（说明是动态注册物品）。

> 若用户从未导入源 B，不得报错、不得弹窗骚扰，静默使用源 A。

### 源 C：现有配方数据库（必须实现，不是可选项）

用户点击侧边栏物品后要能看到"这东西怎么做出来的"「制作」与"这东西能干嘛"「用途」，因此必须把整合包里**已有的全部配方**解析成可检索的索引。这是 3.5 节配方浏览视图的数据基础。

**扫描范围**（三处，按游戏加载顺序合并，同 ID 后者覆盖前者）：

1. **jar 内数据驱动配方**：`mods/*.jar` 中的 `data/<ns>/recipes/**/*.json`（1.21+ 部分为 `data/<ns>/recipe/**`，两种路径都要扫）
2. **数据包配方**：`<modpack>/kubejs/data/**/recipes/**/*.json`、`<modpack>/config/openloader/data/*/data/**/recipes/**/*.json`、`<modpack>/datapacks/*.zip` 内的同路径
3. **KubeJS 脚本配方**：`<modpack>/kubejs/server_scripts/**/*.js`（以及 `kubejs/server_scripts/` 下用户新增的脚本）

**通用启发式解析**（这是核心要求：**禁止为每个模组写专属解析器**，配方 JSON 结构千差万别，必须用一套启发式覆盖）

```json
{
  "type": "minecraft:crafting_shaped",
  "pattern": ["AA", "AA"],
  "key": { "A": { "item": "minecraft:oak_log" } },
  "result": { "item": "minecraft:oak_planks", "count": 4 }
}
```

解析算法：

1. `type` 字段 → 配方类型 ID
2. **输出**：优先读 `result` / `results` / `output` / `outputs` / `output_item` / `main_output` 字段；若都不存在，递归遍历所有字段，收集**键名含 `result` / `output` / `to` / `produce`** 的物品引用对象
3. **输入**：递归遍历，收集 `ingredients` / `input` / `inputs` / `key` / `catalyst` / `base` / `addition` / `template` / `tool` 等键下的物品引用；`pattern` 必须配合 `key` 展开为实际物品列表（`pattern` 里的字符 → `key` 查表）
4. **物品引用识别**（全部要支持）：`{ "item": "ns:id" }`、`{ "tag": "ns:tag" }`、`{ "id": "ns:id" }`、`{ "fluid": "ns:fluid" }`、`{ "fluidStack": { "fluid": ... } }`、`{ "items": ["ns:a","ns:b"] }`、纯字符串 `"ns:id"`
5. **数量**：`count` / `amount` / `chance`
6. **解析不了不中断**：标记 `partial: true`，但仍把已提取到的产物 ID 建进索引——保证「制作」Tab 至少能列出它，卡片上标注「解析不完整」

**存储优化（硬性要求）**：

扫描阶段**只存摘要，绝不保存完整 JSON 到内存或磁盘**。大型整合包（GTNH 类）配方 JSON 可达 15 万条以上，全量常驻必然 OOM。

```ts
interface RecipeRecord {
  uid: string        // "jar:create-1.20.1.jar#data/create/recipes/mixing/foo.json"
  type: string       // "create:mixing"
  outputs: { id: string; count: number; kind: 'item' | 'fluid'; chance?: number }[]
  inputs:  { id: string; count: number; kind: 'item' | 'fluid' | 'tag' }[]
  source: 'jar' | 'datapack' | 'kubejs'
  sourcePath: string
  partial: boolean
}
```

- 内存倒排索引：`byOutput: Map<string, number[]>`、`byInput: Map<string, number[]>`
- 用户**点击某个配方卡片要载入工作台时**，才用 `yauzl` 按 `sourcePath` 二次打开 jar 惰性读取完整 JSON（读一条关一次，不复用句柄）
- 摘要持久化到 `userData/cache/<hash>/recipes.json`，与物品索引同生命周期失效

**KubeJS 脚本解析（尽力而为）**：

- 用 `acorn` 以 `sourceType: 'script'` 解析 `kubejs/server_scripts/**/*.js`
- 识别调用：`event.shaped` / `shapeless` / `smelting` / `blasting` / `smoking` / `campfire_cooking` / `stonecutting` / `smithing` / `custom` / `event.recipes.<ns>.<method>`
- **只提取字面量参数**（字符串、数字、数组、对象字面量）。遇到变量引用、函数调用、模板字符串插值 → 该配方标 `partial: true`，只记录已解析部分
- 单个脚本解析失败记 `WARN` 日志并跳过，不影响其他脚本
- 这类配方 `source: 'kubejs'`，卡片显示「来自现有脚本」徽章，并在「载入工作台」时提示「原始脚本含动态逻辑，仅载入可静态解析的部分」

**配方数量展示**：索引完成后顶栏或状态条显示「配方库：128,432 条（原版 3,102 / 模组 124,880 / KubeJS 450）」。

## 3.4 工作台与交互

中间区域有**两个视图**：`配方浏览`（见 3.5，点击侧边栏物品进入）与 `工作台`（本节，用于构建新配方）。两者共用同一份工作台状态，来回切换不丢失内容。

工作台由「配方类型选择器 + 槽位区 + 产物槽」组成，**形态由配方类型的 schema 决定，不是写死的 3×3**。

### 配方类型与布局的映射

```ts
type LayoutKind =
  | 'shaped'        // 有序网格，默认 3×3，可由 schema 指定 rows/cols（最大 9×9）
  | 'shapeless'     // 无序材料列表（可增删行）+ 产物槽
  | 'single_io'     // 单输入槽 + 产物槽（熔炉/高炉/烟熏/切石）
  | 'multi_io'      // 输入列表 + 输出列表（Create 搅拌、IE 粉碎）
  | 'sequence'      // 嵌套配方序列编辑器（Create 序列组装，见 3.6.12）
  | 'custom'        // 由 schema 提供格子坐标数组（Botania 花瓣药房的 16 格环形）
```

- `shaped` 渲染有序网格，默认 3×3，用户可切换 3×3 / 2×2 / 1×1；Create 机械合成由 schema 指定为最大 9×9。生成脚本时自动去掉全空的行列（**这是 KubeJS 有序合成的硬性要求，多余的空白行会导致匹配失败**）
- `shapeless` / `single_io` / `multi_io` 渲染动态行列表，每行 = 一个物品槽 + 数量输入 + 删除按钮，底部「+ 添加材料」
- `sequence` 渲染嵌套配方序列编辑器（见 3.6.12），每个步骤是一张可配置的子配方卡片
- `custom` 按 schema 提供的格子坐标数组绝对定位渲染（如 Botania 花瓣药房的 16 格环形布局）


### 四类槽位

1. **材料槽**：接受物品、流体（若 schema 声明）、标签（`#tag`，用户可手动输入）
2. **产物槽**：接受物品、流体，带数量与概率（0–100%，部分模组支持）
3. **辅助槽**：模具（Create 序列组装）、催化剂（Thermal）、燃料等，由 schema 的 `extraSlots` 声明
4. **注册表槽**：承载非物品的注册表对象（灌注类型 / 气体 / 浆液 / 色素），详见下节

### 注册表槽：非物品参数怎么承载

**问题起点**：Mekanism 的冶金灌注配方需要一个「灌注类型」+ 用量，而灌注类型**不是物品**——它是 `mekanism:infuse_type` 注册表里的条目（`mekanism:redstone` / `mekanism:carbon` / `mekanism:diamond` / `mekanism:refined_obsidian` …），不在物品索引里。

```js
event.recipes.mekanism.metallurgic_infusing(
  'minecraft:comparator',      // 产物
  'minecraft:nether_quartz',   // 输入物品
  'mekanism:redstone',         // ← 灌注类型：注册表对象，不是物品 ID
  20                            // ← 用量：独立于物品数量
)
```

同类情况还有 `gas`（气体）、`slurry`（浆液）、`pigment`（色素），以及其它模组类似的注册表引用。它们都必须在 UI 上被正确承载，否则这类配方**根本没法编辑**。

**UI 规范**：

| 项    | 规范                                                                                       |
| ---- | ---------------------------------------------------------------------------------------- |
| 视觉区分 | 注册表槽用**紫色系**底纹 `rgba(160,120,230,.14)` + 边框 `rgba(160,120,230,.45)`，与物品槽（灰）、流体槽（蓝）三者一眼可分 |
| 槽内显示 | 注册表缩写角标：`INF`（灌注）/ `GAS`（气体）/ `SLR`（浆液）/ `PGM`（色素），配该项的类型主色                              |
| 填入方式 | **不从侧边栏拖拽**。改为**点击槽位弹出专用选择面板**                                                           |
| 选择面板 | 宽 320px 浮层，锚定在槽位下方；顶部搜索框（气体有几十种，必须能搜）；列表每项 = 类型色块 + 中文名 + ID；底部用量输入框（默认 10）；点击条目即填入并关闭   |
| 键盘   | `↑`/`↓` 移动、`Enter` 确认、`Esc` 关闭、面板内 `Ctrl+F` 聚焦搜索                                         |

> **为什么不做成侧边栏可拖拽项**：灌注类型一共 8–12 种，混进四万条物品的列表里会污染搜索结果，用户更难找；而且每个配方类型所需的注册表不同，全局切换器反而累赘。点槽位弹出是最短路径。

**图标例外**：注册表类型多数没有独立 PNG，图标打包在 GUI 精灵图集里，按坐标裁切成本高、易错。**允许**用「类型主色块 + 缩写」表示——这是全程序**唯一**允许不使用真实贴图的地方（物品仍严格禁止）。

**取值来源三级**（按优先级合并）：

1. **ProbeJS 注册表声明** —— 最全，能覆盖"模组注册了但本包没用到"的值
2. **从本包配方样本归纳** —— 扫描所有 `infusionInput` 等字段的实际值去重，最贴合当前整合包（L1 反推天然产出这份数据，零额外成本）
3. **内置常见列表** —— 前两者都不可用时的兜底

**代码生成的两种形态（不要共用模板）**：

```js
// 灌注类型：作为独立字符串参数 + 独立数量参数
event.recipes.mekanism.metallurgic_infusing(
  'minecraft:comparator',
  'minecraft:nether_quartz',
  'mekanism:redstone',
  20
)

// 气体：打包成一个对象参数
event.recipes.mekanism.purifying(
  'minecraft:obsidian',
  'minecraft:lava_bucket',
  { gas: 'mekanism:oxygen', amount: 200 }
)
```

对应的数据包 JSON 形态也不同：

```json
{
  "type": "mekanism:metallurgic_infusing",
  "input": { "amount": 1, "ingredient": { "item": "minecraft:nether_quartz" } },
  "infusionInput": { "amount": 20, "tag": "mekanism:redstone" },
  "output": { "item": "minecraft:comparator" }
}
```

> 这就是 schema 必须能描述**参数形态**（独立标量 / 打包对象）而不只是"参数列表"的原因。字段名与嵌套结构以 L1 从真实样本反推的结果为准，上面两段仅作示意。

### Schema 驱动的动态渲染（一套组件适配全部配方类型）

**核心原则：不为「配方类型」写界面，只为「参数形态」写控件。**

一个 400 模组的整合包有 600–1200 种配方类型。如果按类型写 UI，这条路从第一天就走不通。正确做法是：**参数只有 11 种形态，控件只有 11 个，任意配方类型都是这 11 个控件的不同组合。**

#### 参数 → 控件映射表（唯一的映射关系）

| `kind` | 条件 | 渲染控件 |
|---|---|---|
| `item` | `multiple: false` | 单个物品槽（34×34） |
| `item` | `multiple: true` | 物品槽列表 + 增删按钮 |
| `fluid` | — | 流体槽 + mB 数字输入 |
| `tag` | — | 标签槽（自动补 `#` 前缀，支持 `forge:` 提示） |
| `registry` | — | 注册表槽（点击弹选择面板，见上节） |
| `number` | — | 数字输入框（带 `min`/`max` 校验提示） |
| `boolean` | — | 开关 |
| `choice` | — | 分段选择器（选项 ≤ 5）或下拉（> 5） |
| `text` | — | 单行文本框 |
| `struct` | — | 字段分组容器（递归渲染其子字段） |
| `unknown` | — | 键值对编辑器（兜底，见三级降级） |

**这 11 个控件是全部。** 任何模组、任何配方类型，都只能用这 11 个组合出来。

#### 主参数 / 次要参数：自动分层

参数数量从 2 个到 7 个不等（实测 PressurizedReaction 有 7 个）。不能平铺，否则界面会很乱。程序按 `kind` 自动分层：

| 层级 | 包含的 kind | 视觉处理 |
|---|---|---|
| **主参数** | `item` / `fluid` / `tag` / `registry` | 大尺寸槽位，占视觉重心 |
| **次要参数** | `number` / `boolean` / `choice` / `text` | 小尺寸控件，聚成一行放在下方 |
| **未知参数** | `unknown` | 折叠在「高级参数」区，默认收起 |

于是 7 个参数的 PressurizedReaction 在视觉上变成：**3 个槽位 + 4 个数字/开关**，结构清晰。

#### 视觉顺序 ≠ 参数顺序（容易忽略的坑）

KubeJS 的调用顺序是 `(output, itemInput, chemicalInput)`——**产物在第一个**。但按合成直觉，产物应该在**右侧**。

所以渲染时不能照参数顺序排，必须按语义重排：

```
判定规则：
  字段名含 output / result / outputs / result_item  → 视觉右侧（产物区）
  字段名含 input / ingredient / catalyst / template → 视觉左侧（材料区）
  其余                                              → 视觉下方（附加区）
```

这条不处理，界面会出现「产物在最左边、材料在右边」的反直觉布局。

#### 通用值模型：让切换类型时数据能带走

工作台**不存**"3×3 网格"或"材料列表"这类结构，而存一个通用字典：

```ts
interface BenchValues {
  [slotKey: string]: SlotValue | SlotValue[] | number | boolean | string | null
}
```

由 schema 解释这个字典怎么渲染。带来三个好处：

1. **切换配方类型时尽可能保留已有值**：从 `crafting_shaped` 切到 `create:mixing`，材料数组和产物能带走，用户不用重填
2. **载入现有配方**只需把解析结果填进字典，不需要为每种类型写转换代码
3. **撤销/重做**只需快照这个字典，与 schema 无关

保留策略：切换类型时按 `slotKey` 同名匹配 → 名称近似匹配（`ingredients` ↔ `ingredients`）→ 无法匹配的丢弃，并在 toast 里说明「3 个材料已保留，2 个字段因类型不兼容已清除」。

#### 三级降级（保证任何情况都能编辑）

| 级别 | 触发条件 | 表现 |
|---|---|---|
| **一级** | schema 完整（插件 / L0 / ProbeJS / L1 成功） | 标准表单，全部控件正常 |
| **二级** | 部分字段类型为 `unknown` | 已知字段正常渲染；未知字段进「高级参数」折叠区，用键值对编辑器 |
| **三级** | 完全无法解析 | 纯 JSON 编辑器 + 提取到的产物/主输入仍作为槽位显示 |

三级永远是可用的，这是底线。

#### 响应式：表单随容器宽度自适应

中间区宽度会因为拖拽侧边栏/代码栏而变化（约 480–900px）。表单必须：

- 用 CSS Grid 的 `auto-fit` + `minmax` 排布槽位组，宽度不足自动换行
- 主参数区与产物区之间用箭头连接，**窄屏时箭头改向下的 `↓`**，布局从横向变纵向
- 次要参数用 `flex-wrap`，一行放不下自动折行
- 断点不做固定像素判断，用 `ResizeObserver` 观察容器实际宽度

#### 三个实例对比（同一渲染器，三个不同界面）

以实际提取的 Mekanism schema 为例：

| 类型 | 参数 | 渲染结果 |
|---|---|---|
| `ItemToItem`（crushing 等） | output, input | 单行：[输入槽] → [产物槽]，极简 |
| `MetallurgicInfusing` | output, itemInput, chemicalInput | 双行：[物品槽][注册表槽 ×20] → [产物槽] |
| `PressurizedReaction` | 7 个参数 | 主体：[物品槽][流体槽] → [产物槽]；下方一行：能量 / 时长 / 开关；折叠区：气体输入输出 |

**同一套控件，三种完全不同的界面，零类型专属代码。**

### 两个硬骨头：9×9 网格与仪式配方

通用表单能覆盖绝大多数类型，但有两类必须单独设计。它们的难点完全不同：**Create 机械合成难在空间，Occultism 仪式难在语义。**

#### A. Create 机械动力合成器（9×9）—— 难在空间

**问题**：9×9 = 81 格。按常规 48px 槽位算，光网格就要 450px 宽，加上产物区，中间区（最窄约 480px）放不下；纵向 81 格 × 48px = 432px，也会把日志区挤没。

**关键判断：9×9 是上界，不是常态。** 真实配方绝大多数在 5×5 以内：

```js
event.recipes.create.mechanical_crafting('minecraft:emerald', [
  ' DDD ',
  'D D',
  'D D',
  'D D',
  ' DDD '
], { D: 'minecraft:dirt' })
```

绝大多数玩家一辈子也写不出 9×9 的配方。所以**不要一上来就画 81 格**。

**渲染规则**：

1. **按内容自适应起始尺寸**：以非空单元格的最小包围盒作为初始网格（上例渲染 5×5，而不是 9×9）
2. **可手动扩展**：底部提供「+ 行」「+ 列」按钮，最大扩到 9×9；扩展出来的空行空列用**更淡的边框**表示"已扩展待填"，与"有意义留空"区分
3. **格子尺寸随规模动态计算**，用 CSS 变量而非固定值：

```css
--cell: clamp(24px, calc((100% - 140px) / var(--cols)), 48px);
```

4. **缩放控制**：右上角 `75% / 100% / 150%`，同时支持 `Ctrl + 滚轮`
5. **网格区独立滚动**：格子溢出时只滚动网格容器，不带动整个页面滚动

尺寸对照：

| 网格规模 | 格子边长 | 网格总宽 | 观感 |
|---|---|---|---|
| 1–3 | 48px | ≤ 160px | 宽松 |
| 4–6 | 40px | ≤ 250px | 正常 |
| 7–9 | 32px | ≤ 300px | 紧凑但可读 |

**生成时复用同一套裁剪逻辑**：按最小包围盒裁剪后输出 pattern，与 `crafting_shaped` 完全共用代码，不要为 9×9 重写一份。

#### B. Occultism 仪式 —— 难在语义

**问题**：不是网格，而是「1 个激活物 + 最多 12 个材料 + 一个法阵等级 + 两个布尔前置」。而且每个字段名对用户都是天书。

**渲染规则**：

1. **顶部前置条件摘要条**（见 3.6.13），把「要摆什么阵、要不要献祭」先说清楚
2. **激活物单独成区**，用**琥珀色边框 + 「激活」角标**，与普通材料明确区分
   > 这是这类型最容易搞错的地方：用户会理所当然地以为激活物也是丢进碗里的材料之一，实际上它是点金碗用的
3. **材料区用 4×3 网格，而不是纵向列表**：12 个槽纵向排需要 500px 高，横排 4 列 3 行只要 150px
4. **法阵等级用分段选择器**（Tier 1–4 四档），每档配一个对应 chalk 颜色的小色块（白 / 金 / 紫 / 红），把"等级"和"用什么颜色的粉笔"的对应关系直接可视化
5. **两个布尔开关**紧挨法阵等级，文案写成完整句子：「仪式中需活体献祭」「需手持物品右键」，不要只写字段名

布局：

```
┌──────────────────────────────────────────────────────────────┐
│ ⚠ 需要 巨灵法阵(Tier2) · 12 个材料 · 无需献祭 · 激活物《绑定之书》 │
├──────────────────────────────────────────────────────────────┤
│  ◆ [激活物]  绑定之书（巨灵）          ← 琥珀色边框           │
├──────────────────────────────────────────────────────────────┤
│  ┌──┬──┬──┬──┐                                              │
│  │■ │■ │■ │■ │                                              │
│  ├──┼──┼──┼──┤     ➜     ┌────┐                             │
│  │■ │■ │■ │■ │           │ ■  │  传送矩阵                    │
│  ├──┼──┼──┼──┤           └────┘                             │
│  │■ │■ │■ │■ │                                              │
│  └──┴──┴──┴──┘                                              │
├──────────────────────────────────────────────────────────────┤
│  法阵  [T1白][T2金][T3紫][T4红]    ☐ 活体献祭   ☐ 物品使用      │
└──────────────────────────────────────────────────────────────┘
```

**为什么不做成真正的五芒星环形布局**：听起来很酷，但用户要的是"快速改配方"，不是看仪式预览。环形排布会让"第 7 个材料在哪"变得难找，反而拖慢操作。**可用性优先于拟真。**

如果确实想要仪式感，可以做一个**只读的阵型预览小图**放在角落（展示 chalk 颜色与符文的相对位置），但它不参与编辑——编辑区永远用高效网格。

| 操作                            | 行为                                               |
| ----------------------------- | ------------------------------------------------ |
| **从侧边栏拖拽物品 → 材料槽**            | 放入该槽位；若槽位已有物品则**替换**；Alt+拖拽为「插入到该位置并后移」          |

| **Alt + 左键点击侧边栏物品**           | 快捷路径：跳过吸取流程，直接填入当前激活槽位（不用双击，避免与"单击打开配方浏览"冲突）     |

| **在产物槽中输入 `2x`**              | 支持数量前缀语法：输入框接受 `2x minecraft:xxx` 或独立数量字段        |

### 中键采用「吸取—放置」两阶段模型（不要做成一次性填入）

这是刻意选择的设计，不是实现偷懒。理由有四条：

1. **一次性填入依赖"激活槽位"这个隐式状态** —— 用户很容易忘记当前焦点在哪个槽，结果东西填到了错误位置，且没有明显反馈
2. **两阶段模型让"放哪里"由落点显式决定** —— 与吸色笔的直觉一致：先吸取，再吐出
3. **材料槽与产物槽共用同一套放置逻辑** —— 用户不需要记忆"哪个组合键对应哪种槽"，点在哪儿就是哪儿
4. **吸取状态下所有可放置槽位高亮** —— 等于把「当前可交互范围」可视化了，降低试错成本

配套的视觉要求：

- 手持图标跟随光标，略微旋转（约 -8°）并带投影，模拟"捏在手里"的物理感
- 底部常驻「吸色条」：显示当前吸取的物品名 + 操作提示（点击放置 / Shift 连续 / Esc 取消）
- 所有可放置槽位在吸取态下边框转品牌色，hover 时变实线并轻微放大 1.08
- 放置动画：图标从光标位置飞入槽位（约 120ms），**不要瞬间出现**

**中键关键实现注意**：浏览器中键会触发 `auxclick` 及 Windows 自动滚动模式。必须监听 `mousedown` 判断 `e.button === 1`，并 `e.preventDefault()` 阻止默认行为，且阻止 `auxclick` 冒泡。

**拖拽视觉**：使用 dnd-kit 的 `DragOverlay` 渲染跟随鼠标的物品图标 + 名称标签；目标槽位在悬停时显示 2px 品牌色描边与轻微放大；非法目标显示红色禁止光标。

### 撤销 / 重做

工作台的全部变更（槽位设置、数量、类型切换、产物变更）必须进入历史栈，`Ctrl+Z` / `Ctrl+Shift+Z` 可回退至少 100 步。历史栈记录完整快照（配方对象很小，直接存快照，不要做复杂 diff）。

点击卡片后：

1. 自动切换到 `工作台` Tab
2. 配方类型切换到该配方的 `type`：若内置 schema 中存在 → 直接使用对应布局；**若不存在 → 自动进入「⚙ 通用 / 任意模组配方」兜底模式**，把完整 JSON 铺进 `extras`

## 3.6 配方类型系统与多模组覆盖

**绝对不要**用一个巨大的 `if/else` 或 `switch` 硬编码模组配方。也**不要**指望靠人工枚举内置库覆盖所有模组——一个 400 模组的整合包，配方类型总数在 **600–1200 种**区间，人工枚举不可能覆盖，且不同 Mod 版本字段还会变。

### 3.6.1 关键前提：`event.recipes.*` 来自附属模组，不是 KubeJS 本体

**这是整个多模组支持的地基，必须在 P2 扫描阶段就解决，不能等到生成代码时才发现。**

KubeJS 官网 FAQ 原文：

> "If the mod uses datapack recipes, then it's supported by default. Some more complicated mods require addon mods, but in theory, still would work with datapack recipes."

拆解成三条确定性事实：

1. **数据驱动的模组，KubeJS 默认支持** —— 走 `event.custom({ type: ... })` 或数据包 JSON
2. **`event.recipes.<ns>.<method>()` 语法糖需要额外安装附属模组** —— KubeJS Create、KubeJS Thermal、KubeJS Mekanism 都是 CurseForge 上**独立发布**的模组，不是 KubeJS 本体自带
3. **没装附属模组时语法糖不存在** —— `event.recipes.create` 是 `undefined`，生成的脚本在游戏里会直接抛 `TypeError` 而整段失效

**因此程序必须做附属模组检测，并据此决定生成哪条通道：**

| 检测结果               | 生成方式                                                     |
| ------------------ | -------------------------------------------------------- |
| 装了 `kubejs_create` | `event.recipes.create.mixing(...)`（语法糖）                  |
| 未装附属，但装了 `create`  | `event.custom({ type: 'create:mixing', ... })` 或数据包 JSON |
| 主模组都没装             | 该类型标记为不可用，从下拉中隐藏                                         |

**检测方法**：扫描 `mods/*.jar` 中的 `META-INF/mods.toml`（Forge/NeoForge）或 `fabric.mod.json`（Fabric），读出 `modId` 集合。常见附属关系（**仅作提示，实际以扫描结果为准，不要用硬编码表判定**）：

```
kubejs_create   → create        kubejs_thermal   → thermal
kubejs_mekanism → mekanism      kubejs_immersive_engineering → immersiveengineering
kubejs_ars_nouveau → ars_nouveau  kubejs_botania → botania
```

**UI 必须显性呈现能力**，在每个配方类型右侧显示徽章：

- `✓ 语法糖` — 附属模组已装，生成简短优雅的代码
- `✓ 兼容` — 附属未装，将以 `event.custom` / 数据包 JSON 生成
- `✗ 不支持` — 模组硬编码配方，无法通过 KubeJS 添加

设置页提供「KubeJS 附属模组」面板，列出已装/未装并给出可操作建议：

> 「你安装了 Create，但未安装 KubeJS Create。Create 配方将以 `event.custom` 形式生成。如需语法糖写法，请加装 KubeJS Create。」

### 3.6.2 能力边界以「配方类型」为单位，不是「模组」

这一点容易被忽略：**同一个模组内，不同配方类型的支持程度并不一致**。所以能力标注的粒度必须是 `recipe type`。

以 Mekanism 为例（**实测自 `kubejs-mekanism-forge-2001.1.5.1-build.2.jar`，而非官网文档**）：

| 配方类型 | 支持情况 |
|---|---|
| crushing / enriching / smelting / combining / compressing / purifying / injecting / metallurgic_infusing / sawing / chemical_infusing / crystallizing / dissolution / energy_conversion | ✓ 有语法糖 |
| activating / centrifuging / evaporating / gas_conversion / oxidizing / nucleosynthesizing / pigment_mixing / pigment_extracting / painting / reaction / rotary / separating / washing / infusion_conversion | ✓ **实测有语法糖**（官网标为 Broken/Unsupported，已过时） |
| Boiler、Phase Shifter (SPS) | ✗ 无 RecipeType，任何方式都无法添加 |

> **重要教训**：kubejs.com 的 Mekanism 页仍把 12 个类型列为「Broken / Unsupported」，但 2001.1.5.1 版本的 jar 里实际注册了 **27 个 type、23 个 RecipeSchema**。若按官网清单写死能力判定，会误判一半以上的可用类型。
> **能力判定必须以 jar 实物为准，文档只能作为线索。** 详见 3.6.15 的实测方法与数据。

由此得出分类（UI 上如实标注，不给虚假承诺）：

| 类别                          | 特征                 | 支持程度               | 实现手段                            |
| --------------------------- | ------------------ | ------------------ | ------------------------------- |
| **A. 有 KubeJS 语法糖**         | 附属模组已装且实现了该方法      | 完整体验（结构化表单 + 简洁代码） | 语法糖直出                           |
| **B. 仅数据驱动 RecipeType**     | 配方库中存在该 `type` 的样本 | 完整体验（结构化表单）        | `event.custom({...})` 或数据包 JSON |
| **C. 硬编码配方 / 无 RecipeType** | 配方库无样本、ProbeJS 无声明 | **不支持**            | UI 明确标注，不提供该类型                  |


> A + B 覆盖绝大多数模组。C 类本来也无法通过 KubeJS 添加——如实告知比假装支持更有价值。  
> 判定依据：该 `type` 是否在整合包配方库（3.2 源 C）中存在样本，或是否在 ProbeJS 声明中注册。可在设置中手动解除误判。

**三个典型模组的实测写法差异**（说明为什么不能靠一套模板硬编码）：

| 差异维度            | Create                                                                | Thermal                                                                           | Mekanism                                        |
| --------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------- |
| 方法名风格           | `create.mixing()` 与 `createMixing()` 两种都可用                            | `thermal.pulverizer()`                                                            | `mekanism.crushing()` 与 `mekanismCrushing()` 两种 |
| 概率输出写法          | `CreateItem.of('ns:id', 0.5)` 或 `Item.of('5x ns:id').withChance(0.5)` | `Item.of('ns:id').withChance(0.5)`                                                | `item.of('ns:id').chance(0.3)`（仅部分类型）           |
| `withChance` 语义 | 0–1 的纯概率                                                              | **同一参数既表数量又表概率**：`withChance(4.5)` = 4 个 + 50% 概率第 5 个；`withChance(0.05)` = 5% 概率 | —                                               |
| 流体/气体参数         | `Fluid.of('ns:fluid', mb)`                                            | 同 Create                                                                          | 气体用对象：`{ gas: 'mekanism:oxygen', amount: 200 }` |
| 字符串歧义           | **无法区分物品与流体，默认按流体解析** → 必须 `Ingredient.of()` 显式包裹                     | 无此问题                                                                              | 无此问题                                            |
| 多输入             | 数组 `[a, b]`，顺序无关                                                      | 数组或单值                                                                             | 固定位置参数 `(output, input1, input2)`               |
| 链式修饰符           | `.heated()` `.superheated()` `.processingTime(ms)` `.keepHeldItem()`  | `.energy(fe)` `.water(mb)`                                                        | —                                               |

**结论**：这些差异既无法用统一模板生成，也无法靠人工枚举穷尽。反推法只关心 **JSON 字段**（模组的数据格式稳定），JS 写法差异交由各模组的 schema 处理——这是唯一可扩展的路径。

### 3.6.3 五层 Schema 来源（这才是"支持所有模组"的实现）

```
插件  可插拔扩展      第三方 / 整合包作者提供，精准覆盖特定模组（见 3.6.14）
L0   内置精校库        人工编写，字段名与显示名最准确，体验最好
L1   从现有配方反推    自动，扫描整合包真实配方归纳字段 —— 覆盖任意模组，可扩展性核心
L2   ProbeJS 类型推断  自动，从 .d.ts 方法签名拿参数语义（需用户导入）
L3   通用手工模式      终极兜底，用户手填 JSON 字段
```

> 插件是**加速层不是必需层**：没装插件时 L1 照样能覆盖该模组，只是字段名不够友好、没有前置条件提示。两者叠加而非替代。

**合并策略（关键，不要简单地"后者覆盖前者"）：**

- 以 **插件 / L0** 为骨架。若两者都无此 `type`，则用 **L1** 生成完整 schema
- **L1 对骨架做字段校验与补全**：L1 样本中出现频率 ≥10% 但骨架未定义的字段，追加为可选字段，标记「整合包实测字段」；骨架有但 L1 样本中从未出现的字段，降级为「高级（未在本包出现）」折叠区。这样能自动适配同一模组的不同版本
- **L2 提供语义命名**：把 `ingredient` / `result` 映射成中文显示名与更准确的槽位类型
- **用户手动钉住的修改优先级最高**，一旦钉住，该类型不再被插件 / L1 / L2 覆盖
- 每个 schema 全程携带 `source` 与 `sampleCount`，UI 卡片角标显示可信度

### 3.6.4 L1 核心算法：从真实配方反推 schema

**这是让"支持所有模组"真正落地的一层。** 前提是 3.2 源 C 已经解析出全整合包的配方摘要，因此天然拥有每种 `type` 的真实样本。

按 `type` 分组 → 每组采样 → 归纳结构：

```
1. 分组：Map<type, recipeUid[]>，直接由 records 按 type 聚合
2. 采样：每组取 min(50, n) 个，优先 partial=false 的样本
3. 读取：用 yauzl 惰性读取这些样本的完整 JSON（复用 3.2 的惰性通道）
4. 归纳：递归遍历（深度上限 3），对每个 JSON 路径记录
      - 出现次数 / 采样总数          → 出现率
      - 值类型（string/number/bool/object/array）
      - 是否数组 / 数组元素结构是否一致
5. 字段筛选：
      出现率 = 100%           → required
      10% ≤ 出现率 < 100%     → optional
      出现率 < 10%            → 丢弃（多为罕见兼容字段，纳入只会干扰）
6. 类型判定（按值形状优先于 JSON 类型）：
      所有值是 { item | tag | id }          → itemRef（物品槽）
      所有值是 { fluid | fluidStack }        → fluidRef（流体槽）
      所有值是数字                           → number（记录 min/max 作为校验提示）
      所有值是字符串且唯一值 ≤ 20            → choice（枚举出所有可能值）
      所有值是字符串                         → text
      所有值是布尔                           → boolean
      混合类型                               → unknown（渲染成 JSON 文本域）
7. 结构判定：
      该路径在所有样本中都是数组 → multiple: true
      数组元素结构一致 → 递归提取元素 schema
        （例：result 数组每项 {item, count, chance} → 生成「产物列表」槽组）
8. 语义命名：查常见字段词典，未命中则用字段名本身
      ingredient→原料  result→产物  energy→耗能  time→耗时  experience→经验
      chance→概率  temperature→温度  fluid→流体  count→数量  catalyst→催化剂
      pattern→排列  key→图例  tool→工具  base→基底  addition→添加物
9. 产出 RecipeTypeSchema(source: 'inferred', sampleCount: n)
```

**约束（必须在 UI 与日志中体现）：**

- 反推出的类型在下拉中单独分组「本包实测」，并标注「基于 47 个真实配方归纳」
- `sampleCount < 3` 的类型标记 `lowConfidence`，表单下方黄条提示「样本过少，字段可能不全，可手动补充」
- 反推结果可被用户「钉住」成自定义 schema（写入 `userData/customRecipeTypes.json`），之后优先于 L1
- **反推一律只生成字段结构，不生成默认值**——避免给用户预填错误的数值
- 反推失败（样本 JSON 全部无法解析）时，该 type 退化为 L3 通用模式，并记 `WARN` 日志

### 3.6.5 多模组并存的冲突与顺序（必须处理）

多模组场景下的四类真实冲突，每一条都要有明确策略：

**① 配方类型 ID 冲突 —— 天然隔离**

`thermal:pulverizer` 与 `create:mixing` 带命名空间，不会撞名。但**同一 `type` 名可能被多个模组复用**（如都用 `minecraft:crafting_shaped`）。因此 **L1 反推必须按 `type` 全局分组统计，不能按模组分组**，否则同一类型的字段集会被割裂。

**② 配方 ID 覆盖链 —— 必须展示，否则用户改了不生效**

`data/<ns>/recipes/<path>.json` 同路径会被后者覆盖，加载顺序为「模组 jar → 数据包 → `kubejs/data`」。整合包里三个来源同时定义一个配方是常态。

程序必须保留**完整定义链**，在配方卡片与「载入工作台」后的提示条显示：

> ⚠ 该配方被 3 处定义，当前生效：`kubejs/data/mypack/recipes/foo.json`  
> （被覆盖：`thermal-1.20.1.jar#data/thermal/recipes/foo.json`、`config/openloader/data/x/...`）

生成新配方时若目标 ID 已被占用，写入前必须给出同样提示，询问「覆盖 / 另存为新 ID」。

**③ 脚本加载顺序 —— 影响 `event.remove` 与同 ID 覆盖**

KubeJS 按**文件名典序**加载 `server_scripts/*.js`。程序生成的文件统一命名为 `recipe_studio_<时间戳>.js`，多个生成脚本之间的生效顺序由时间戳决定。

必须做到：

- 若同一会话内生成多个脚本，文件名时间戳递增加 `_01`、`_02` 后缀，保证顺序可预期
- 生成「移除配方」时，UI 明确提示：`event.remove` 在配方注册后统一执行，不受文件名顺序影响，但**多个脚本先后 remove 同一 ID 时，后执行者才是最终结果**
- 提供「脚本执行顺序」面板：列出 `server_scripts/*.js` 按加载顺序编号，可一键重命名为 `01_`/`99_` 前缀来调整

**④ 跨模组物品依赖 —— 靠全局索引，无需特殊处理**

A 模组的配方用 B 模组的物品是常态。物品索引本身就是全局的（按 ID 索引，不按模组），天然支持。唯一要注意的是：若被依赖的模组未安装，该 ID 在索引中不存在，配方卡片上显示 `⚠ 未知物品`，但不阻断载入与生成。

### 3.6.6 输出通道双轨（终极兼容性保障）

生成结果支持两种落地形式，用户可在「写入文件」时选择：

|         | **模式 A：KubeJS 脚本**           | **模式 B：数据包 JSON**                               |
| ------- | ---------------------------- | ----------------------------------------------- |
| 写入路径    | `kubejs/server_scripts/*.js` | `kubejs/data/recipe_studio/recipes/<name>.json` |
| 兼容性     | 依赖 KubeJS 版本语法，跨版本有差异        | **任意版本、任何数据驱动模组 100% 支持**                       |
| 条件逻辑    | 支持 JS 变量、循环、条件               | 不支持                                             |
| 移除原配方   | 支持 `event.remove`            | 不支持（需另用脚本）                                      |
| 单条配方可读性 | 好                            | 好（纯 JSON）                                       |
| 多配方批量   | 好（一个文件多个）                    | 每条一个文件                                          |

**通道选择由 3.6.10 的判定逻辑自动决定，不是让用户盲选：**

| 条件                 | 自动选择                 | 用户可见提示          |
| ------------------ | -------------------- | --------------- |
| 附属模组已装且实现该方法       | 模式 A（语法糖）            | `✓ 语法糖`         |
| 附属模组未装，但配方库有样本     | **模式 B（数据包 JSON）**   | `✓ 兼容 · 已切换数据包` |
| 需要在脚本里统一管理 / 含条件逻辑 | 模式 A（`event.custom`） | 用户可手动覆盖         |
| 用户明确要求不依赖脚本层       | 模式 B                 | —               |

### 语法糖能力可能弱于原始 JSON —— 必须支持自动降级

装了附属 ≠ 能写全部参数。**KubeJS 附属提供的语法糖往往是原始配方的真子集。**

Immersive Engineering 的附属只提供这三个重载：

```js
event.recipes.immersiveengineeringArcFurnace([输出], 输入)
event.recipes.immersiveengineeringArcFurnace([输出], 输入, [添加物])
event.recipes.immersiveengineeringArcFurnace([输出], 输入, [添加物], 矿渣)
```

**没有 `energy`、没有 `time`、没有概率副产物 `secondaries`。** 也就是说即使装了 KubeJS IE，用语法糖也只能写出一个残缺的电弧炉配方——这也是社区教程里普遍反映「KubeJS 改电弧炉写不了概率和时间」的原因。

**规则**：schema 中每个字段标记 `sugarSupported: boolean`。当用户填了任何一个语法糖无法表达的字段时：

1. 自动从语法糖切换到 `event.custom`
2. 代码预览上方显示黄条：「已从语法糖切换为 `event.custom` —— `energy`、`time`、`secondaries` 无法通过语法糖表达」
3. 日志记 `INFO`，说明降级原因

**绝不允许**为了用语法糖而丢弃用户填的参数，也不允许生成一个"看起来对但少了一半参数"的配方。

> 为什么"附属未装"时优先数据包 JSON 而不是 `event.custom`：官方 FAQ 明确"still would work with datapack recipes"，数据包是绕过 KubeJS 脚本引擎、不受版本语法差异影响的最短路径。`event.custom` 保留为需要统一脚本管理时的备选。

用户始终可以手动覆盖自动选择（「写入文件」对话框里有通道切换），但默认必须是能跑通的那条。

> 模式 B 是完全绕过 KubeJS 脚本引擎的兜底：`kubejs/data/` 会被当作数据包加载，任何注册了 `RecipeType` 的模组都能读取。这条通道是"支持所有模组"的实际保障。

生成模式 B 时，`type` 字段直接取原始 RecipeType ID，其余字段按反推出的 schema 原样序列化，不做任何语法转换。

**数据包 JSON 的命名空间**：默认用 `recipe_studio`，写入前检查 `mods/*.jar` 中是否已存在同名 namespace，冲突则自动加后缀 `recipe_studio2`。配方文件名用 `<type路径>_<产物id>_<序号>.json`，保证可读且不冲突。

### 3.6.7 Schema 定义

```ts
interface RecipeTypeSchema {
  id: string                    // "create:mixing"
  displayName: string           // "Create · 搅拌"
  modId: string                 // "create"
  modDisplayName: string        // "Create"
  source: 'builtin' | 'inferred' | 'probejs' | 'custom'
  /** 反推来源的样本数，用于可信度展示 */
  sampleCount?: number
  lowConfidence?: boolean
  /** 用户是否钉住（钉住后不再被 inferred/probejs 覆盖） */
  pinned?: boolean
  layoutKind: LayoutKind
  /** 生成函数名，如 "event.recipes.create.mixing"；为 null 时走 event.custom */
  emitTarget: string | null
  /** emitTarget 为 null 时的 JSON 模板 */
  customTemplate?: Record<string, unknown>
  slots: RecipeSlotSchema[]
  outputs: RecipeSlotSchema[]
  /** 整合包实测存在但内置库未定义的字段，折叠展示 */
  extraFields?: RecipeSlotSchema[]
  supportsChance?: boolean
  modifiers?: ModifierSchema[]
  docUrl?: string
}

interface RecipeSlotSchema {
  key: string                   // "ingredient"
  displayName: string           // "原料"
  kind: 'item' | 'fluid' | 'tag' | 'text' | 'number' | 'boolean' | 'choice' | 'registry' | 'unknown'
  /** kind==='registry' 时必填，指明注册表 ID，如 "mekanism:infuse_type" */
  registry?: string
  /** 参数在 JS 调用中的形态：独立标量，还是与其他字段打包成对象 */
  emitShape?: 'scalar' | 'object' | 'positional'
  multiple: boolean             // 是否接受多个值（列表）
  required?: boolean            // 由出现率推导
  min?: number
  max?: number
  choices?: { value: string; label: string }[]
  defaultValue?: unknown
}
```

### 3.6.8 兜底：通用模式（必须实现）

配方类型下拉的**最底部**固定一项「⚙ 通用 / 任意模组配方」。选中后工作台变成一个自由表单：

- 「配方类型 ID」输入框（如 `thermal:pulverizer`），带自动补全——候选来自本次扫描到的**全部真实 `type`**（含反推结果），这是最可靠的候补源
- 「输入槽」列表 / 「输出槽」列表（与多输入单输出布局一致）
- 「额外 JSON 字段」键值编辑器（key / value，value 支持 JSON 字面量）
- **若该 type 已有反推 schema，自动把字段预填成对应表单控件**，而不是留空让用户手写
- 生成结果一律为 `event.custom({ type: '...', ... })`（模式 A）或原生 JSON（模式 B）

**这是保证"支持所有模组"的最后一道通道，必须优先实现并稳定可靠。**

### 3.6.10 覆盖率保障：怎么做到"所有能加的都能加"

**核心思路：程序不预设任何模组清单，而是从整合包自身推导出"可用配方类型全集"。** 这是覆盖率的根本保证——不需要代码里认识这个模组，只要整合包里有它的配方，程序就能处理。

**类型全集 = 三源并集**

1. jar 内 `data/*/recipes/**/*.json` 出现过的**所有 `type` 值**
2. 数据包 / `kubejs/data` / `kubejs/server_scripts` 中出现的所有 `type` 值
3. ProbeJS 声明的全部 `RecipeType`（用于捕获"模组注册了类型、但整合包里恰好没用到"的遗漏）

> 推论很重要：**只要某模组的配方是数据驱动的，整合包里必然存在该类型的样本文件**。所以扫一遍配方库，就等于拿到了"这个整合包能加哪些配方"的完整清单。程序不需要维护模组名单。

**逐类型判定 + 通道选择（保证每条都能落地）**

```
for each type in 类型全集:
    hasSample   = 配方库中存在该 type 的样本
    hasSyntax   = 对应附属模组已安装且实现了该方法
    hasProbeJS  = ProbeJS 中有该类型的声明

    schema = hasSample ? inferSchema(samples)          // L1 反推
           : hasProbeJS ? fromProbeJS()                // L2 推断
           : null                                      // 只能 L3 手填

    channel = hasSyntax ? 'kubejs-sugar'               // 语法糖
            : hasSample ? 'datapack-json'              // 数据包 JSON（最稳）
            : 'event-custom'                           // event.custom
```

**通道优先级的关键调整**：当附属模组未实现该方法时，**默认走数据包 JSON 而不是 `event.custom`**。原因：官方 FAQ 明确指出"still would work with datapack recipes"，数据包 JSON 是绕过 KubeJS 脚本层的最短路径，不受 KubeJS 版本语法差异与 `event.custom` 兼容性影响。`event.custom` 仅作为需要写在脚本里统一管理时的备选。


**覆盖率自检面板**（设置页 → 诊断，必须实现）

导入整合包后自动统计并展示，让用户一眼看到到底覆盖了多少：

```
本整合包配方类型覆盖情况
─────────────────────────────────────────
  扫描到的配方类型          847 种
  ├─ 可结构化编辑           812 种  (95.9%)   ← 表单化，不用手写 JSON
  ├─ 仅通用模式可编辑        35 种  ( 4.1%)   ← 手填字段，仍可生成
  └─ 完全无法添加             0 种

生成通道分布
  ├─ KubeJS 语法糖          128 种   （附属模组已装）
  ├─ 数据包 JSON            719 种   （附属未装，自动切换）
  └─ event.custom             0 种
─────────────────────────────────────────
附属模组检测
  ✓ kubejs_create        ✓ kubejs_thermal     ✗ kubejs_mekanism（建议安装）
```

**硬性要求**：禁止在 UI 或日志中给出"该模组不支持"这类笼统结论。必须精确到 `recipe type`，并同时给出可执行的替代方案（换通道 / 装附属 / 确认是否真无 RecipeType）。

**诚实的边界**：确实存在无法添加的配方类型——模组在 Java 里硬编码、完全没有注册 `RecipeType` 的（如 Mekanism 的 Boiler、SPS）。这不是程序缺陷，是 Minecraft 生态的客观限制。程序的责任是**准确识别并如实告知**，而不是让用户反复尝试后才发现失败。

### 3.6.11 兼容性设计原则：不依赖对附属模组的认知

附属模组（KubeJS Create / Thermal / Mekanism / IE / Ars / Botania…）数量多、API 各不相同、跨版本还会变。**如果程序靠"内置知识"去拼这些 API，必然不兼容。** 因此定下一条不可违反的设计原则：

> **程序绝不内建「我知道某个附属模组的 API 长什么样」这类假设。每一个决策的依据都必须来自整合包本身。**

| 决策        | 依据来源                                    | 是否依赖认知 |
| --------- | --------------------------------------- | ------ |
| 有哪些物品     | jar 内 lang 文件的 `item.<ns>.<id>` 键       | 否，纯事实  |
| 能加哪些配方类型  | jar / 数据包中出现的所有 `type` 值                | 否，纯事实  |
| 每种类型有哪些字段 | 归纳该 type 的真实配方样本（L1）                    | 否，纯事实  |
| 附属模组是否可用  | `mods.toml` / `fabric.mod.json` 的 modId | 否，纯事实  |
| 语法糖的方法签名  | ProbeJS 导出的 `.d.ts`（当前包的实际声明）           | 否，读当前包 |

**这就是它能兼容任意附属模组的原因——它不需要"知道"，只需要"读"。**

### 三条通道的耦合度对比

| 通道                    | 依赖什么                 | 与附属模组的耦合 | 兼容性风险          |
| --------------------- | -------------------- | -------- | -------------- |
| KubeJS 语法糖            | 方法名 + 参数顺序 + 修饰符链    | **强耦合**  | 高：API 一变即失效    |
| `event.custom({...})` | 仅 KubeJS 的 custom 入口 | 弱        | 中：依赖 KubeJS 版本 |
| **数据包 JSON**          | **只依赖配方 JSON 结构**    | **零耦合**  | **无**          |

### 关键：数据包 JSON 直接绕开了附属模组

必须看清这层因果：

```
event.recipes.create.mixing(A, B, C)      ← 附属模组提供的 JS 语法糖
        ↓  附属模组内部翻译
{ "type": "create:mixing", "ingredients": [...], "results": [...] }
        ↓
注册给 Create 的 RecipeType                ← Create 真正读取的东西
```

**附属模组只是 JS 语法糖的翻译层。** 它翻译出来的那个 JSON，才是模组真正消费的内容。

所以直接写那个 JSON，就**完全不需要附属模组存在**，也不受其 API 任何变化的影响。

这一条把"每个模组都有独立 KJS，程序怎么兼容"的担忧从根上消解了：**附属 API 怎么变都无所谓，因为可以选择完全不经过它。**

### 版本差异的处理顺序

同一附属模组跨版本 API 会变（例：KubeJS Create 同时存在 `create.mixing()` 与 `createMixing()` 两种风格）。处理顺序固定为：

1. **优先读 ProbeJS 导出** —— 它描述的是**当前这个整合包、当前这个版本**的真实签名，不是程序作者的记忆
2. 无 ProbeJS → 使用内置精校库，并标注「未在本包验证」
3. 以上都不可靠 → **自动降到数据包 JSON**，绕开 API 差异

程序**绝不**因为"内置库说应该这么写"就强行生成语法糖。

### 生成前的结构校验（不依赖 API 也能抓错）

写盘前除 acorn 语法检查外，还必须做**语义结构校验**（基于反推 schema，与任何附属 API 无关）：

- 必填字段是否齐全（`required: true` 的）
- 字段形态是否匹配（该是数组却给了单值 / 该是物品对象却给了纯字符串）
- 引用的物品 ID 是否存在于索引中（不存在则警告「未知物品」，不阻断）
- 流体量是否为正整数、概率是否落在合法区间

校验失败则阻止写盘并定位到具体字段。**这套校验完全基于整合包事实，因此对任何模组都成立。**

### 生成偏好开关（给用户掌控权）

设置中提供三档，默认「自动」：

| 偏好         | 行为                                         |
| ---------- | ------------------------------------------ |
| **自动**（默认） | 按 3.6.10 的判定逻辑选通道，保证一定能跑通                  |
| 始终语法糖      | 强制生成 `event.recipes.*`；附属缺失时**明确报错**而非静默降级 |
| 始终数据包 JSON | 完全绕开脚本层，生成纯 JSON                           |

### 验收口径（写进 README）

> 程序对「模组 KJS 支持」的承诺不是"我认识所有附属模组"，而是：  
> **只要某个配方类型在整合包里以数据驱动形式存在，程序就能为它生成可用的配方。**  
> 附属装了就用语法糖，没装就写数据包 JSON，API 变了就绕开——  
> 功能不因附属模组的差异而缺失。

### 3.6.12 参数形态原语：特殊配方怎么收敛

Mekanism 灌注只是冰山一角。模组配方千奇百怪，但**不要去枚举特殊**，而要抽象出有限的原语。任何配方参数，拆到底都是这 9 种形态的组合：

| # | 原语                     | JSON 特征                                  | UI 渲染方式        | 典型例子                          |
| - | ---------------------- | ---------------------------------------- | -------------- | ----------------------------- |
| 1 | **scalar**             | 字符串 / 数字 / 布尔                            | 文本框 / 数字框 / 开关 | Botania 的 mana 数值、Astral 的星辉量 |
| 2 | **reference**          | `{item}` / `{tag}` / `{fluid}` / `{gas}` | 引用槽（点击选择）      | 普通输入物品                        |
| 3 | **reference + amount** | `{item,count}` / `{amount,tag}`          | 引用槽 + 数量输入     | Mekanism 灌注类型 × 20            |
| 4 | **list**               | 数组                                       | 可增删行列表         | 多输入、多概率输出                     |
| 5 | **struct**             | 固定字段对象                                   | 分组表单           | Thermal 催化剂倍率组                |
| 6 | **nested recipe**      | **对象内自带 `type` 字段**                      | **子配方序列编辑器**   | Create 序列组装                   |
| 7 | **modifier**           | 顶层可选字段 / 链式方法                            | 附加选项区（开关 + 数值） | `.heated()`、`energy`          |
| 8 | **nbt**                | `{ item, nbt: {...} }`                        | NBT 角标 + 展开编辑器（复杂时降级 JSON） | 附魔书、Apotheosis 词条 |
| 9 | **blockstate**         | `{ block: { id, ...属性 } }`               | 方块选择器 + 属性键值表（单值/多值/范围） | AE2 熵变臂、Botania 纯雏菊 |

**这就是为什么 L1 反推能覆盖未知模组**：它不关心这是哪个模组的配方，只判断每个字段属于哪种原语。

### 形态自动识别规则（L1 反推时执行）

```
对每个字段值：
  字符串形如 ns:id 且命中物品索引            → reference(item)
  字符串形如 ns:id 但不在物品索引            → reference(registry) 或 tag，按上下文判定
  对象含 { amount, tag|item|fluid|gas }     → reference + amount
  对象自身含 "type" 字段                     → ★ nested recipe（嵌套配方）
  数组                                     → list（递归分析每个元素）
  数字 / 布尔                               → scalar
  对象含 { id, ...属性 } 且 id 是方块        → ★ blockstate（方块状态 + 属性匹配）
  对象含 { item|tag, nbt }                  → reference + nbt（带 NBT 约束的物品）
  其余对象                                  → struct（递归展开其字段）
```

**最关键的一条是 `对象自身含 "type" 字段 → nested recipe`。** 这条规则能自动发现"配方里套配方"的情况（Create 序列组装就是典型），不需要预先知道哪个模组会这么干。

### 配对字段合并（不做这一步，界面会散架）

原始 JSON 里「一个物品 + 一个数量」通常写成两个字段：

```json
{ "base_ingredient": { "item": "minecraft:iron_ingot" }, "count": 4 }
{ "output": { "item": "minecraft:gold_nugget" }, "chance": 0.2 }
{ "fluid": "immersivepetroleum:diesel", "amount": 27 }
```

如果直接按字段平铺渲染，用户会看到一个物品槽、旁边一个孤零零的数字框，还得自己猜"这个数字是数量还是概率"。**必须识别并合并成复合控件**。

**配对模式表**（L1 反推时优先匹配，命中即合并）：

| 模式 | 键组合（任一侧） | 合并后的控件 |
|---|---|---|
| 计数物品 | `{item / ingredient / base_ingredient / result}` + `{count / size}` | 物品槽 + 右下角数量徽章 |
| 概率物品 | `{item / output / result / byproduct}` + `{chance / probability}` | 物品槽 + 概率角标（如 `20%`） |
| 流体量 | `{fluid / fluidstack}` + `{amount}` | 流体槽 + mB 输入 |
| 带量标签 | `{tag}` + `{amount}` | 标签槽 + mB 输入 |
| 注册表量 | `{tag / infuse_type / gas}` + `{amount}` | 注册表槽 + 用量 |

**合并规则**：

- 两个字段的键名命中同一模式，且**在样本中总是成对出现**（共现率 > 95%）→ 合并
- 合并后原键名保留在 `compound: ['count']` 中，生成 JSON 时能还原回去
- 只有当配对模式**匹配不上**时，才退回"独立字数字段"

> 这一步是"通用表单"与"好用表单"的分水岭。没做合并，IE 电弧炉会被渲染成 9 个互不相干的字段，用户根本不知道该填什么。

### 实例：同样叫「多产物」，IE 和 IP 结构完全不同

这是"为什么不能硬编码"的最好证据。两个模组的配方都有"多个产物 + 概率副产物"，但 JSON 结构毫无共性。

**Immersive Engineering 电弧炉**：

```json
{
  "type": "immersiveengineering:arc_furnace",
  "input": { "tag": "mekanism:crystals/allthemodium" },
  "additives": [ { "tag": "mekanism:alloys/atomic" }, { "tag": "mekanism:alloys/atomic" } ],
  "results": [ { "base_ingredient": { "tag": "mekanism:crystals/allthemodium" }, "count": 1 } ],
  "secondaries": [ { "chance": 0.2, "output": { "tag": "forge:ingots/allthemodium" } } ],
  "slag": { "tag": "forge:slag" },
  "energy": 6144000,
  "time": 6000
}
```

**Immersive Petroleum 蒸馏塔**：

```json
{
  "type": "immersivepetroleum:distillation",
  "input": { "tag": "forge:crude_oil", "amount": 75 },
  "results": [ { "fluid": "immersivepetroleum:lubricant", "amount": 9 },
               { "fluid": "immersivepetroleum:diesel", "amount": 27 },
               { "fluid": "immersivepetroleum:gasoline", "amount": 39 } ],
  "byproducts": [ { "item": "immersivepetroleum:bitumen", "chance": "0.07" } ],
  "energy": 2048,
  "time": 1
}
```

**差异对照**：

| 语义 | IE 电弧炉 | IP 蒸馏塔 | 是否兼容 |
|---|---|---|---|
| 主输入 | `input` (纯引用) | `input` (`{tag, amount}`) | ✗ 结构不同 |
| 副材料 | `additives[]` | 无 | — |
| 主产物 | `results[{base_ingredient, count}]` | `results[{fluid, amount}]` | ✗ 物品 vs 流体 |
| 概率副产物 | `secondaries[{chance, output}]` | `byproducts[{item, chance}]` | ✗ 键名与嵌套都不同 |
| 固废 | `slag` | 无 | — |
| 概率类型 | 数字 `0.2` | **字符串 `"0.07"`** | ✗ 类型都不同 |

**这就是为什么必须靠 schema 而不是硬编码**：同样是"概率副产物"，一个是 `{chance, output}`，一个是 `{item, chance}`，概率一个用数字一个用字符串。

靠配对字段合并 + struct 原语，两者都能被正确识别并渲染成「物品槽 + 概率角标」。**程序不需要知道这是 IE 还是 IP。**

### 三类必须专门做 UI 的特殊情况

绝大多数配方靠「通用表单 + 引用槽 + 修饰符区」就能覆盖。只有这三类超出通用表单能力，必须单独实现组件：

**① 嵌套配方（Create 序列组装）**

配方参数里包含一整个配方数组：

```js
event.recipes.create.sequenced_assembly(
  [output], 'input',
  [
    event.recipes.create.deploying(...),   // ← 子配方
    event.recipes.create.cutting(...),
    event.recipes.create.pressing(...)
  ]
).transitionalItem('create:incomplete_x').loops(4)
```

UI 需要「**序列步骤编辑器**」：垂直排列的步骤卡片，每步可选步骤类型（deploying / cutting / pressing / filling）并各自配置其参数；底部设置过渡物品与循环次数。这是真正意义上的"配方里嵌配方"，普通表单做不了。

**② 可变尺寸网格**

现有 `LayoutKind.shaped` 固定 3×3，但：

- Create 机械合成最大 **9×9**
- Botania 花瓣药房是**固定 16 格环形 + 中心物品**的特殊排布

需要扩展 `LayoutKind`：新增 `grid_nxn`（带 `rows`/`cols` 参数，1×1 到 9×9）与 `custom`（由 schema 提供格子坐标数组）。

**③ 修饰符链**

`.heated()` / `.superheated()` / `.processingTime(500)` / `.keepHeldItem()` / `.energy(4000)` / `.water(400)`

UI 渲染为「附加选项」区域，不是槽位。开关型用 checkbox，数值型用数字框，生成时按 schema 声明的顺序追加到调用链末尾。

### 兜底：形态无法归类时降级为原始 JSON 编辑器

若某个 type 的样本结构过于怪异（字段过多、嵌套过深、无法归入上述 7 种），**不要勉强拼表单**，直接降级为：

- 完整 JSON 编辑器（带语法高亮与字段级校验）
- 常用字段（产物、主要输入）仍提取为槽位供可视化操作
- 其余字段在 JSON 区手动编辑
- 生成时走 `event.custom` 或数据包

这是"至少还能编辑"的底线保障，比什么都不给强得多。

### 实现优先级

1. 先做 9 种原语的通用渲染（覆盖 90%+ 类型）
2. 再做引用槽与选择面板（含注册表槽）
3. 再做修饰符区
4. 然后做可变网格（含 9×9）
5. 嵌套配方编辑器放最后（复杂度最高，但只有 Create 序列组装等少数类型需要）
6. 全程保留原始 JSON 降级通道

### 3.6.13 语义层：字段名对人可读（以 Occultism 为反面教材）

**Occultism 的仪式配方，数据一点都不复杂：**

```json
{
  "type": "occultism:ritual",
  "activation_item": { "item": "occultism:book_of_binding_bound_djinni" },
  "pentacle_id": "occultism:craft_djinni",
  "require_sacrifice": false,
  "require_item_use": false,
  "ritual": { "item": "occultism:ritual_dummy/craft_dimensional_matrix" },
  "ingredients": [ { "tag": "quark:crystal_clusters" }, { "item": "eidolon:ender_calx" }, "…共 12 项" ],
  "result": { "item": "occultism:dimensional_matrix" }
}
```

拆开看就是：一个不定长数组（4）+ 若干引用（2）+ 两个布尔（1）+ 一个字符串枚举（choice）。**9 种原语完全够用**，L1 反推能自动识别。

**但它对用户极其不友好**：

| 字段 | 用户看到 | 实际含义 |
|---|---|---|
| `pentacle_id` | 完全不懂 | 必须摆「巨灵法阵」，要用金粉笔、蜡烛、骷髅摆对位置 |
| `require_sacrifice` | 不知干什么 | 仪式进行中要在法阵内亲手杀一只生物 |
| `activation_item` | 以为是普通材料 | 这是点击金色献祭碗用的激活物，不是消耗品 |
| `ritual` | 以为是产物 | 这是 JEI 显示用的占位 dummy 物品 |

> **真正难的不是数据结构，而是语义。** 程序生成的代码没错，但用户在游戏里做不出来，等于失败。

**三层命名词典**：

| 层 | 来源 | 示例 |
|---|---|---|
| 1 内置词典 | 预置常见字段映射 | `pentacle_id` → 「法阵等级」、`infusionInput` → 「灌注物」、`activation_item` → 「激活物」 |
| 2 模式推断 | 按命名规律归类 | `*_id` → 「XX 等级/类型」；`require_*` → 「需要 XX」；`*Mod` → 「倍率」；`*_item` → 「XX 物品」；`*_tag` → 「XX 标签」 |
| 3 原样回退 | 无匹配时 | 字段名转空格分隔的可读形式 |

**枚举值也要有词典**（很多模组在 lang 文件里提供了本地化名，优先取它）：

```
occultism:craft_foliot → 狐狸精法阵（Tier 1）
occultism:craft_djinni → 巨灵法阵（Tier 2）
occultism:craft_afrit  → 阿夫利特法阵（Tier 3）
```

**前置条件摘要条（仪式 / 祭坛 / 多结构类配方必须做）**

这类配方的难点不在生成代码，而在**游戏内怎么摆**。用户改完配方后若不知道需要什么法阵、要不要献祭，进游戏必然做不出来。

schema 需支持给字段声明 `role: 'requirement'`，UI 在工作台上方自动汇总成一条摘要：

```
⚠ 该仪式需要：巨灵法阵（Tier 2） · 12 个材料 · 无需活体献祭 · 激活物《绑定之书（巨灵）》
```

同类需要摘要条的还有：Blood Magic 祭坛（血量 + 层级）、Botania 符文祭坛（符文类型）、Tconstruct 浇筑（铸模 + 冷却）。**凡是「配方数据之外的摆放/操作要求」，就要在摘要条里讲清楚。**

**虚拟物品必须从索引中过滤**

Occultism 有大量 `ritual_dummy/*`、`jei_dummy/*` 物品，它们只用于 JEI 图标显示，不是真实物品。

物品索引时要识别并标记 `virtual: true`，默认在侧边栏隐藏（设置里可开启显示）：

- ID 的 path 含 `dummy` / `display` / `jei_`
- 或该物品在 lang 中无任何显示名
- 或它的唯一用途是作为 `ritual` 这类显示字段的值

否则用户会在物品列表里撞见一堆毫无意义的 `ritual_dummy/craft_xxx`，非常干扰。

### 3.6.14 插件系统：把模组支持做成可插拔的

**动机**：靠程序内置 schema 库追不上模组生态。KubeJS 本身就是「本体 + 附属模组」的插件化架构，本程序沿用同一思路——**让模组支持成为可插拔的插件**，谁了解这个模组，谁就能写它的插件。

**关键定位：插件不是必需项，是加速项。** 没有插件时 L1 反推照样能覆盖该模组的配方（只是字段名不友好、无前置条件提示）；装了插件则体验完整。两者是叠加关系，不是替代关系。

**插件形态：JSON 为主，JS 钩子为辅**

| 形态 | 能力 | 安全性 |
|---|---|---|
| **JSON 声明式**（首选） | 声明配方类型、参数 schema、字段中文名、枚举值名、生成模板 | 无代码执行，绝对安全 |
| JS 钩子（可选） | 自定义代码生成函数（复杂模板场景） | Node `vm` 沙箱，禁用 `require`/`fs`/网络，1s 超时 |

**插件不得自定义 UI 组件**，只能从程序内置的布局原语（`shaped` / `shapeless` / `single_io` / `multi_io` / `sequence` / `custom`）中选。这样能保证所有插件出来的界面风格一致，不会变成一堆野路子界面。

**插件清单结构**

```jsonc
{
  "id": "occultism-ritual",
  "name": "Occultism 仪式支持",
  "version": "1.0.0",
  "author": "…",
  "appVersion": ">=1.0.0",          // 兼容范围，不匹配则跳过并警告
  "mods": ["occultism"],             // 需要安装哪些模组（未装则整包禁用）
  "kubejsAddon": null,               // 若为 "kubejs_create"，则仅在该附属存在时启用语法糖
  "recipeTypes": [ /* 见下 */ ],
  "fieldNames": { "pentacle_id": "法阵等级" },
  "valueNames": { "occultism:craft_djinni": "巨灵法阵（Tier 2）" },
  "virtualItemPatterns": ["occultism:ritual_dummy/*"]
}
```

**配方类型声明示例**（以 3.6.13 的 Occultism 为例）：

```jsonc
{
  "id": "occultism:ritual",
  "displayName": "神秘学 · 仪式",
  "layoutKind": "multi_io",
  "emitTarget": null,                       // null 表示走 event.custom / 数据包
  "customTemplate": { "type": "occultism:ritual" },
  "slots": [
    { "key": "activation_item", "displayName": "激活物", "kind": "item",
      "multiple": false, "required": true, "role": "requirement" },
    { "key": "ingredients", "displayName": "祭祀材料", "kind": "item",
      "multiple": true, "min": 1, "max": 12 },
    { "key": "pentacle_id", "displayName": "法阵等级", "kind": "choice",
      "choicesSource": "values:pentacle_id", "role": "requirement" },
    { "key": "require_sacrifice", "displayName": "需要活体献祭", "kind": "boolean",
      "defaultValue": false, "role": "requirement" },
    { "key": "require_item_use", "displayName": "需要物品使用", "kind": "boolean",
      "defaultValue": false }
  ],
  "outputs": [
    { "key": "result", "displayName": "产物", "kind": "item", "multiple": false }
  ]
}
```

`role: "requirement"` 的字段会被汇总进 3.6.13 说的「前置条件摘要条」。

**插件能声明什么（共 8 项）**

1. 配方类型列表及其 `layoutKind`
2. 每个类型的参数 schema（slots / outputs / emitShape / 约束）
3. 代码生成目标（`emitTarget`）或 JSON 模板（`customTemplate`）
4. 字段中文名词典
5. 枚举值中文词典
6. 前置条件角色标记（`role: requirement`）
7. 依赖的模组 / KJS 附属（`mods` / `kubejsAddon`）
8. 虚拟物品过滤规则

**插件可以只声明一部分**——例如只提供 `fieldNames` 让字段名可读，参数结构仍由 L1 反推填充。这种"部分覆盖"能力让写插件的门槛很低。

**加载与优先级**

```
用户手动钉住的修改   ← 最高，任何来源都不覆盖
插件（本包 → 用户目录）
内置精校库 L0
ProbeJS 推断 L2
L1 反推             ← 兜底，永远可用
```

**加载来源**（前者优先）：

1. `<整合包>/.recipe-studio/plugins/` —— **跟随整合包分发**
2. `userData/plugins/` —— 用户级，跨整合包复用

> 第 1 条是这套设计最有价值的地方：**整合包作者可以为自己包的魔改打包插件**，玩家导入整合包即自动获得精确的配方编辑支持，不需要额外装任何东西。

**与附属模组检测联动**

插件声明 `kubejsAddon: "kubejs_create"` 时：

- 该附属已安装 → 用 `emitTarget` 生成语法糖代码
- 该附属未安装 → **自动降级为数据包 JSON**，并在插件管理页显示「因未安装 KubeJS Create，已切换为数据包模式」

插件与 3.6.1 的附属检测直接打通，不需要用户手动判断。

**安全与健壮性约束**

1. JSON 插件严禁任何形式的代码执行
2. JS 钩子在 `vm` 沙箱中运行，注入白名单 API，1 秒超时强杀
3. **插件加载必须隔离**：单个插件解析失败只记 WARN 并跳过，绝不阻断启动
4. 同 `type` 被多个插件声明时，按来源优先级取第一个，并在插件页标出冲突
5. `appVersion` 不匹配的插件跳过加载，但保留在列表中显示为「不兼容」，不静默消失

### 3.6.15 实证：直接从 jar 读取 RecipeSchema（Mekanism 实测）

**为什么这条路优于 ProbeJS**：ProbeJS 要求玩家进游戏执行一次导出命令，多一道前置操作。而 KubeJS 附属的 `*RecipeSchema` 类就在 jar 里躺着，编译产物结构高度固定，完全可以离线解析。

**KubeJS RecipeSchema 的固定字节码模式**

每个附属的 Schema 接口源码都长这样：

```java
public interface MetallurgicInfusingRecipeSchema {
  RecipeKey<OutputItem> OUTPUT = ItemComponents.OUTPUT.key("output");
  RecipeKey<ItemStackIngredient> ITEM_INPUT = MekComponents.INPUT_ITEM.key("itemInput");
  RecipeKey<InfusionStackIngredient> CHEMICAL_INPUT =
      MekComponents.INFUSE_TYPE_INPUT.key("chemicalInput").optional(/* 默认值 */);
  RecipeSchema SCHEMA = new RecipeSchema(
      MekanismRecipeJS.class, MetallurgicInfusingRecipeSchema::new,
      OUTPUT, ITEM_INPUT, CHEMICAL_INPUT);
}
```

编译后每个字段都是同一组指令，模式完全可预测：

```
getstatic  RecipeComponent.XXX      // 字段类型
ldc        "fieldName"              // 字段名
invokeinterface RecipeComponent.key // 生成 RecipeKey
invokevirtual   RecipeKey.optional  // 可选：标记非必填并给默认值
putstatic                           // 存入静态字段
```

末尾 `new RecipeSchema(..., anewarray RecipeKey[]{...})` 的数组顺序 = **参数顺序**。

**因此只需 4 条规则就能完整还原 schema**：

| 提取目标 | 依据 |
|---|---|
| 字段名 | `ldc` 之后的字符串常量 |
| 字段类型 | 紧随其前的 `getstatic` 字段（`OUTPUT` / `INPUT_ITEM` / `GAS_INPUT` / `FLOAT_LONG` …） |
| 参数顺序 | `RecipeSchema` 构造处 `anewarray` 的元素顺序 |
| 是否必填 / 默认值 | 有无 `invokevirtual RecipeKey.optional`，及其前一条压栈常量 |

**不需要完整 JVM 解析器**，只要一个常量池 + 静态初始化块扫描器，约 200 行代码。

**三步提取**

1. `META-INF/mods.toml` → modId、依赖模组与版本区间
2. `*RecipeSchema.class` → 每个类型的参数结构
3. `<Addon>KubeJSPlugin.class` → 注册的 recipe type ID 列表

**实测输出（`kubejs-mekanism-forge-2001.1.5.1-build.2.jar`）**

mods.toml：

```toml
modId = "kubejs_mekanism"
version = "2001.1.5.1-build.2"
dependencies: kubejs >= [2001.6.4-build.121,)  ·  mekanism >= [10.4.5,)
```

Plugin 类里注册了 **27 个 recipe type**：

|---|---|---|
| ItemToItem | output, input | crushing / enriching / smelting |
| ItemAndGasToItem | output, itemInput, chemicalInput | compressing / purifying / injecting |

2. `chemicalInput` 的默认值从字节码可见是「红石标签 × 10」

**方法论警告（必须遵守）**

> 不要把任何「官网支持清单」硬编码成能力判定表。**文档会过时，jar 不会。**
> 内置的已知清单只能作为 L1 的**提示**，绝不能作为**拒绝依据**。

**实现优先级**

1. ProbeJS 导出（若用户提供）—— 最省事，签名完整
2. **class 文件扫描（本节所述）** —— 离线可用、准确度高，应当默认启用
3. L1 反推 —— 兜底

三者结果合并时：字段名以 1/2 为准，字段类型与必填性交叉校验，冲突时以样本实测（L1）优先。

### 3.6.16 逆天配方图鉴（压力测试清单）

**按「逆天的类型」分类，不要按模组名罗列**——不同类型的应对方式完全不同。

#### 类型 A：数量爆炸型 —— GregTech

**代表**：GregTech CEu / GTNH

- 单个 GTNH 整合包 **30 万+ 条配方**
- 配方**不是 JSON**，而是 Java 代码注册的链式调用
- 配方 ID 是**数字序列**（`gt.recipes.assembler.1`），不是命名空间 ID
- **同一台机器做哪个配方由 circuit 决定**
- 有 voltage tier 概念

KubeJS 语法（GTCEu 官方支持）：

```js
event.recipes.gtceu.assembler('basic_circuit')
  .itemInputs('4x minecraft:redstone', 'minecraft:iron_ingot')
  .inputFluids(Fluid.of('gtceu:soldering_alloy', 72))
  .itemOutputs('gtceu:basic_electronic_circuit')
  .duration(200)
  .EUt(30)
```

**应对**：
- 仍是 struct + list + scalar 的组合，7 原语够用
- `.EUt()` / `.duration()` 归入 modifier（链式修饰符）
- **数量爆炸靠 L1 反推自动吸收**，不预置 30 万条，只归纳类型
- 性能要求：GT 包配方库可达 30 万条，倒排索引内存约 90MB，可接受但需实测

#### 类型 B：输出不是物品 —— Tinkers' Construct

**代表**：匠魂工具组装

- 产出的是**带 NBT 的工具**，属性由部件材料组合动态决定
- 不存在"输入 A+B → 输出 C"的固定映射

**应对**：这**不属于配方系统**，而是"组装系统"。明确不支持并如实告知。但匠魂的**部件配方**（如"铁部件"）本身是普通 shaped，可以正常支持。

#### 类型 C：环境依赖型 —— Astral Sorcery / Thaumcraft

**代表**：星辉（特定星座、夜晚、星辉值）、神秘时代（研究前置）

配方是否生效取决于**游戏内状态**。这不是新原语，而是把 3.6.13 的 `role: requirement` 扩展成结构化声明：

```json
"requirements": [
  { "kind": "structure", "text": "巨灵法阵（Tier 2）" },
  { "kind": "time",      "text": "仅在夜晚生效" },
  { "kind": "dimension", "text": "仅限主世界" },
  { "kind": "research",  "text": "需解锁研究：基础炼金" }
]
```

摘要条按 `kind` 自动选图标与配色，用户一眼能看出"这个配方在什么条件下才成立"。

#### 类型 D：非配方系统 —— Applied Energistics 2 / Integrated Dynamics

- **AE2 的自动合成由玩家在游戏内编码「样板」决定，不存在可生成的数据驱动配方文件**
- 集成动力的"配方"是逻辑卡片连线，本质是可视化编程

**应对**：明确列为不支持，写清原因。但要支持 AE2 的**机器处理配方**（磨粉机、压印器）——那些是真数据驱动。**不要因为"AE2 自动合成不支持"就把它所有类型都隐藏掉。**

#### 类型 E：需要 NBT 匹配 —— 匠魂 / Apotheosis / Curios

```json
{ "item": "minecraft:diamond_sword",
  "nbt": { "Enchantments": [{ "id": "minecraft:sharpness", "lvl": 5 }] } }
```

**这是 7 原语的真正缺口，必须补第 8 种：**

| # | 原语 | UI 渲染 |
|---|---|---|
| 8 | **nbt** | NBT 树编辑器（键值对 + 类型标注），复杂时降级为 JSON 文本框 |

规则：

- 物品槽右上角出现 `NBT` 角标，表示该物品带 NBT 约束
- 点击角标展开 NBT 编辑面板
- 简单 NBT（≤2 层、纯标量）用键值对表单
- 复杂 NBT（深度 > 2 或含数组）降级为 JSON 文本框 + 校验
- **不填 NBT = 不限制 NBT**（这是游戏语义），不要自动塞 `{}`

### 3.6.17 AE2 的配方：大部分正常，三处是坑

不要笼统地说"AE2 不支持"。AE2 的配方有五类，性质完全不同：

| 类型 | 结构 | 能否支持 |
|---|---|---|
| `minecraft:crafting_shaped` / `shapeless` | 标准 | ✓ 完全正常（AE2 大部分配方是这种） |
| `ae2:inscriber` | 命名槽位对象 | ✓ 但有三处需特殊处理 |
| `ae2:charger` / `ae2:matter_cannon` | 标准单进单出 | ✓ 完全正常 |
| `ae2:transform` | 列表 + 环境条件 | ✓ 需顺序约束声明 |
| `ae2:entropy` | **方块状态匹配** | ⚠ 需要新原语 |
| 自动合成样板 | **无数据文件** | ✗ 玩家游戏内编码 |

#### 坑 1：`inscriber` 是命名槽位，且语义是垂直的

```json
{
  "type": "ae2:inscriber",
  "mode": "inscribe",
  "ingredients": {
    "top":    { "item": "ae2:calculation_processor_press" },
    "middle": { "item": "ae2:certus_quartz_crystal" }
  },
  "result": { "item": "ae2:calculation_processor_print" }
}
```

三个问题：

1. **`ingredients` 是命名对象不是数组**（`top` / `middle` / `bottom`），`middle` 必填、`top`/`bottom` 可选 → L1 会正确识别为 `struct`，但
2. **槽位必须垂直排列**，对应压印器机身的三个格子。如果按默认横向排版，用户会完全对应不上机器。schema 需要 `orientation: 'vertical'` 声明
3. **`top` 与 `bottom` 可互换** —— 压印器允许翻转配方，所以「top=A, bottom=B」与「top=B, bottom=A」是同一个配方，**必须做翻转去重检测**，否则用户会做出互相冲突的两个配方

4. `mode` 决定行为差异：`inscribe` 不消耗 top/bottom（压印模板），`press` 会消耗。这个语义要写进字段说明，否则用户不知道为什么模板消失了

#### 坑 2：`entropy` 的输入是「方块状态」不是物品

```json
{
  "type": "ae2:entropy",
  "mode": "heat",
  "input": {
    "block": { "id": "minecraft:cobblestone", "moisture": { "min": 1, "max": 5 } }
  },
  "output": {
    "block": { "id": "minecraft:stone", "keep": true },
    "drops": [ { "item": "minecraft:flint", "count": 1 } ]
  }
}
```

输入是 **blockstate**（方块 ID + 属性匹配），不是物品。属性值支持三种形式：单值、多值数组、`{min,max}` 范围。输出可以同时改方块、改流体、掉物品，`keep: true` 表示继承原方块的属性。

**这是第 9 种原语**，现有 item/fluid/tag/registry 都装不下：

| # | 原语 | UI 渲染 |
|---|---|---|
| 9 | **blockstate** | 方块选择器 + 属性键值表（值支持 单值 / 多值 / 范围 三种输入模式） |

> 这类配方在 MC 里并不罕见（世界交互类：Botania 纯雏菊、Ex Nihilo、AE2 熵变臂都用）。补这一种原语比给每个模组写分支划算。

#### 坑 3：`transform` 的首项约束与环境条件

```json
{
  "type": "ae2:transform",
  "circumstance": "fluid",
  "ingredients": [ {"item":"ae2:charged_certus_quartz_crystal"}, {"item":"minecraft:redstone"} ],
  "result": { "item": "ae2:fluix_crystal" }
}
```

两个隐藏约束：

1. **第一项必须是 `ae2:charged_certus_quartz_crystal`** —— 这是模组代码里的硬性检查，不是数据约定。schema 需要 `firstItemMust: "ae2:charged_certus_quartz_crystal"` 声明，UI 上把它固定为第一个不可删的槽位
2. **`circumstance` 决定触发环境**（`fluid` 扔水里 / `explosion` 被炸），属于 3.6.13 的 `requirements` 范畴

#### 自动合成：确实无解，但不是缺陷

玩家在**样板编码终端**里编码的样板存在存档的 AE 网络 NBT 中，**不存在任何 JSON 文件**。所以：

- 程序读不到，也无从生成
- 但这**不影响** AE2 所有机器配方（压印器、充能器、熵变臂）的编辑
- UI 上应把 AE2 的机器类型正常列出，只在用户问"为什么不能改自动合成"时给出一句解释

> 最忌讳的处理是：因为自动合成做不了，就把整个 AE2 从类型列表里隐藏。那会让用户以为程序连压印器都不支持。

## 3.7 代码生成与写盘

**实时预览**：右侧代码面板用 shiki 高亮 TypeScript/JavaScript 语法，随工作台变更实时刷新（防抖 200ms）。代码只读，但支持一键复制。

**生成模板**（按检测到的 MC 版本切换头部）：

```js
// ── KubeJS Recipe Studio ─────────────────────────────
// Modpack : Nomifactory GTCEu
// MC      : 1.20.1  |  Forge  |  KubeJS 2001.6.5
// Created : 2026-10-30 21:40
// ─────────────────────────────────────────────────────
ServerEvents.recipes(event => {
  event.shaped('4x minecraft:oak_planks', [
    'A',
    'A'
  ], { A: 'minecraft:oak_log' })
})
```

MC ≤1.18 时头部为 `onEvent('recipes', event => { ... })`。

**生成规则细节**：

- 有序合成自动裁剪空白行列（3×3 → 实际最小尺寸），并在 key 中只保留实际使用的符号
- 数量为 1 时省略 `1x ` 前缀
- 流体写作 `Fluid.of('namespace:fluid', amount)`
- 标签写作 `#namespace:tag`
- 多个材料用数组，单个材料也用数组（`event.custom` 中的 `ingredient` 除外，遵循原版 JSON 规范时单数为对象）
- 数字字段不加引号
- **注册表对象**（灌注类型 / 气体 / 浆液）按 schema 的 `emitShape` 决定形态：
  - `scalar`（默认）：输出为字符串字面量 `'mekanism:redstone'`，用量另作独立参数
  - `object`：打包成 `{ gas: 'mekanism:oxygen', amount: 200 }`
  - `positional`：按 schema 声明的参数顺序逐个占位
- 「用量」与「物品数量」是两个独立概念，**绝不合并**：物品用 `count`、流体与灌注用 `amount`，生成时不要互换

**写盘**：

- 目标目录：`<modpack>/kubejs/server_scripts/`
- 目录不存在则创建，并自动生成空的 `kubejs/server_scripts/` 与提示文件
- 默认文件名：`recipe_studio_<yyyyMMdd_HHmmss>.js`，用户可改
- 支持「追加到现有文件」模式（下拉选择 `server_scripts` 下已有的 `.js` 文件），追加时插入到文件末尾的 `ServerEvents.recipes` 块内；无法安全插入则另建文件并提示
- 写盘前做**语法预检**：用 `acorn`（`ecmaVersion: 'latest'`, `sourceType: 'script'`）解析生成代码，失败则阻止写盘并高亮错误行
- 写盘后显示 toast：「已写入 server_scripts/recipe_studio_20261030_214000.js · 在游戏中执行 `/reload` 生效」
- **覆盖已有文件前必须二次确认**，并自动备份原文件到 `kubejs/server_scripts/.backup/<原名>.<时间戳>`

**去重提示**：若生成配方与本次会话已生成的配方结构完全相同，编辑器内显示黄条警告「与已生成的配方重复」。

## 3.8 日志系统

**位置**：底部可折叠抽屉，默认展开 180px，可拖拽至 120–500px，可完全收起（收起时底栏保留一行最新日志）。

**必须包含的元素**：

3. **操作**：清空、复制全部、导出到文件（默认 `userData/logs/studio-<timestamp>.log`）
4. **自动滚动**：默认跟随到底部；用户向上滚动时暂停跟随并显示「↓ 有 3 条新日志」按钮
5. **虚拟滚动**：日志可能上千条，用 `@tanstack/react-virtual` 渲染，上限保留 5000 条（超出丢弃最旧的 DEBUG）

### 3.9.1 骨架尺寸（精确到像素）

| 区域 | 尺寸 | 可调 |
|---|---|---|
| 窗口 | 默认 1440×900，最小 1100×700 | 用户拖拽 |
| 顶栏 | 高 48px，固定 | 否 |
| 左侧边栏 | 宽 320px | 240–520 可拖拽，可整体折叠 |
| 中间主区 | 弹性填充 | 否 |
| 右侧代码栏 | 宽 360px | 280–480 可拖拽，可折叠为标签 |
| 日志抽屉 | 展开 180px | 120–500 可拖拽，可收起（收起保留 32px 单行） |
| 分隔条 | 4px，hover 变品牌色 | — |

**栅格基准 4px**，所有间距取 4 的倍数。圆角：面板 8px、卡片 8px、槽位 4px、按钮 6px、徽章 3px。

### 3.9.2 三栏职责与信息密度

一句话原则：**左找、中改、右看、下记录**。每栏只承担一个认知任务，不混用。

| 区域 | 唯一职责 | 信息密度 | 行高 | 视觉权重 |
|---|---|---|---|---|
| 左侧边栏 | 找物品 | 最高 | 40px（虚拟滚动） | 弱，退到背景 |
| 中间主区 | 看配方 / 改配方 | 中，大量留白 | — | **强，视觉重心** |
| 右侧代码栏 | 只读输出 | 中 | 20px | 弱 |
| 日志抽屉 | 记录与排查 | 高 | 24px | 最弱，默认收起时只留一行 |

三条硬性约束：

1. **中间区必须是最亮的区域**——通过留白与卡片对比实现，而不是靠更亮背景色
2. **侧边栏不做编辑操作**，只做选择与拖拽源；所有编辑发生在中间区
3. **代码栏严格只读**（除复制外无交互），避免用户误以为要在那里改代码

### 3.9.3 视觉层级（表面色阶，最多 4 层）

深色主题靠**明度差**分层，不靠阴影（深色下阴影几乎不可见）。

| 层级 | 用途 | 色值 |
|---|---|---|
| L0 窗口底 | 主内容区背景 | `#0F1115` |
| L1 面板 | 顶栏 / 侧边栏 / 代码栏 / 日志 | `#171A21` |
| L2 卡片 | 配方卡片 / 工作台容器 | `#1E222B` |
| L3 槽位与输入 | 物品槽 / 搜索框 / 代码块 | `#262B36` |

- 边框：常规 `#2A303A`（0.5px），hover `#3A4250`，激活 `#4C8DFF`（2px）
- 选中背景：`rgba(76,141,255,0.14)`
- 文字三级：主 `#E6E8EB` / 次 `#B9BFC9` / 弱 `#5F6B7A`
- 语义色：成功 `#3FB950`、警告 `#D29922`、错误 `#F85149`、链接与强调 `#4C8DFF`
- 字体：UI 用 `-apple-system, "Segoe UI", "Microsoft YaHei", sans-serif`；代码用 `"JetBrains Mono", "Cascadia Code", monospace`
- 字号：标题 14px（weight 500）、正文 13px、辅助 12px、徽章 11px。**不得小于 11px**

浅色主题对应反转：L0 `#F7F8FA` / L1 `#FFFFFF` / L2 `#FFFFFF` + 边框 `#E3E6EB` / L3 `#F1F3F6`，文字 `#1A1D23` / `#4A515C`。

### 3.9.4 槽位渲染规范（物品格）

配方编辑器 80% 的视觉面积由槽位构成，必须严格统一：

| 状态 | 表现 |
|---|---|
| 空槽 | `#262B36` 底 + `#343B47` 1px 内描边 |
| 已填充 | 同底色 + 图标 32×32 居中 + 右下角数量徽章 |
| 悬停 | 描边变 `#3A4250` |
| 吸取态可放置 | 边框转 45% 品牌色；hover 时变实线 2px 并放大 1.08 |
| 激活槽位 | 2px `#4C8DFF` 描边（键盘操作与滚轮调数量的焦点，非中键目标） |
| 拖拽目标合法 | 2px 品牌色虚线框 + 轻微放大 1.05 |
| 拖拽目标非法 | 2px `#F85149` 描边 + `cursor: not-allowed` |
| 只读/禁用 | 整体 40% 不透明度 |

**图标渲染硬要求**：
- **常规显示一律使用真实物品贴图**（从 jar 提取的 PNG），不得用色块、名称首字、emoji 或统一图标代替
- `image-rendering: pixelated`，禁止平滑缩放（MC 材质放大后必须保持像素颗粒感）
- 只允许 16 → 32 → 48 的**整数倍**放大，禁止 1.5× 之类非整数缩放
- 图标缺失时才渲染占位块：`#2A303A` 底 + 名称首字（11px，`#5F6B7A`），**不得留空白**

**数量徽章**：右下角，11px 白字 + `rgba(0,0,0,0.65)` 底 + 3px 圆角 + 2px 内边距。数量为 1 时不显示。

### 3.9.5 交互反馈（每类元素必须三态齐全）

| 状态 | 规范 |
|---|---|
| hover | 背景提亮一档或描边变色，过渡 100ms ease-out |
| active | `transform: scale(0.98)`，60ms |
| focus-visible | 2px 品牌色外描边 + 2px offset，**任何情况下不得用 `outline: none` 移除** |
| disabled | 40% 不透明度 + `cursor: not-allowed`，且不响应 hover |
| 拖拽源 | 原元素 40% 不透明度 + 跟随鼠标的 DragOverlay（图标 + 名称标签） |

过渡统一 `100ms ease-out`，超过 200ms 会让人感觉迟钝。**禁止对布局属性做过渡**（只过渡 `background`/`border-color`/`transform`/`opacity`）。

### 3.9.6 四类状态设计（最容易被忽略，但决定成品感）

**空状态**（三种，各有明确出口）：

| 场景 | 内容 |
|---|---|
| 未导入整合包 | 居中引导卡：`① 导入整合包 → ② 扫描物品与配方 → ③ 拖拽构建配方`，主按钮「选择整合包目录」 |
| 搜索无结果 | 「未找到与 xxx 匹配的物品」+ 次级按钮「清除筛选」+ 提示「支持拼音与首字母，如 jgs」 |
| 配方浏览无配方 | 「暂无已知配方」+ 说明「可能为动态注册配方，或该模组未提供数据驱动配方」 |

**加载态**：
- 首次扫描：侧边栏渲染 8 行骨架屏 + 顶栏进度条 + 进度文字（`正在解析 128/412`）
- 单条配方惰性读取：卡片内局部骨架，不阻塞其他卡片
- **禁止全屏遮罩式 loading**——用户会误以为程序卡死

**错误态**：
- 局部错误 → 内联提示条（黄/红色左边框 + 文字 + 操作按钮），**不用弹窗**
- 全局错误（目录不可读、jar 全失败）→ 顶部横幅，可关闭，不阻断已加载内容
- 只有会导致数据丢失的操作才允许模态确认

**无写入权限**：捕获 `EACCES`/`EPERM` → toast + 提供替代出口「另存到桌面」，而不是只说"失败"。

### 3.9.7 响应式断点

| 宽度 | 行为 |
|---|---|
| ≥ 1440px | 三栏全开，代码栏 360px |
| 1280–1440px | 代码栏收窄至 320px |
| 1024–1280px | 代码栏折叠为右侧标签，点击滑出覆盖层 |
| < 1024px | 侧边栏默认收起，用顶栏图标按钮唤出抽屉 |

窗口尺寸与分隔条位置必须持久化到 `userData/uiState.json`，下次启动恢复。

### 3.9.8 UI 反模式（明令禁止）

1. **禁止**用弹窗承载高频操作（调数量、换物品一律内联完成）
2. **禁止**全屏 loading 遮罩
3. **禁止**深色主题用纯黑 `#000` + 纯白 `#fff`（对比过强刺眼），用 `#0F1115` + `#E6E8EB`
4. **禁止**仅图标无文字的关键按钮（尤其「写入文件」「载入工作台」，必须带文字）
5. **禁止**把日志做成角落小圆点——它必须是一个可展开的完整面板
6. **禁止**在配方卡片内部再套滚动区域（滚动嵌套是操作噩梦）
7. **禁止**槽位尺寸随窗口缩放变形，必须固定整数倍
8. **禁止**用 `alert()` / `confirm()` 原生弹窗

### 3.9.9 键盘可访问性

主流程必须可纯键盘完成：`Tab` 遍历焦点 → `Enter` 触发 → 方向键在物品列表中移动 → `Ctrl+中键` 的等价键位为 `Ctrl+Enter`（设为产物）。焦点顺序遵循视觉顺序：顶栏 → 侧边栏 → 中间区 → 代码栏 → 日志。

**快捷键**：

| 快捷键 | 功能 |
|---|---|
| `Ctrl+F` | 聚焦侧边栏搜索框 |
| `←` / `→` | 配方浏览视图翻页 |
| `Enter` | 载入当前选中的配方卡片 |
| `Tab` | 切换「配方浏览」/「工作台」视图 |
| `Ctrl+Z` / `Ctrl+Shift+Z` | 撤销 / 重做 |
| `Ctrl+S` | 写入文件 |
| `Ctrl+E` | 切换配方类型下拉 |

# 五、关键算法要求

**形状裁剪**（有序合成）：给定 3×3 网格，找出所有非空单元格的最小包围盒，裁剪到该尺寸，并把非空单元格映射为字母 A、B、C…（相同物品复用同一字母），生成 pattern 字符串数组。空行空列必须完全移除。若网格全空则拒绝生成并提示。

**拼音索引**：见 3.3，注意多音字组合上限 8，避免内存爆炸。

**搜索性能**：41,000 条物品，单次查询必须在 **16ms 内**返回（保证输入不卡顿）。实现建议：预把每条记录拼成可检索字段数组，用预编译的正则在已构建的倒排/前缀数组上匹配，避免每次遍历做 `toLowerCase()`。

# 六、错误处理与边界

| 场景 | 要求 |
|---|---|
| 目录无 mods/ | 明确中文错误 + 引导重新选择，不崩溃 |
| jar 损坏 / CRC 错误 | 跳过该 mod，记 `ERROR` 日志，扫描继续，最后汇总「17 个 mod 解析失败」可展开查看 |
| 无 KubeJS | 顶部橙色警告条，仍允许编辑与导出，写入时提示需手动放脚本 |
| kubejs 目录只读 | 捕获 `EACCES`/`EPERM`，提示「无写入权限，请以管理员身份运行或手动导出」 |
| 物品索引为空 | 侧边栏显示空状态 + 「重新扫描 / 检查 mods 目录」按钮 |
| 生成的代码语法错误 | 阻止写盘，代码面板高亮错误行，日志记 `ERROR` |
| 配方类型未选择 | 禁用写入按钮，显示提示 |
| 扫描中途关闭窗口 | 主进程捕获 `before-quit`，中断 worker，清理临时文件 |
| 配方 JSON 结构完全无法识别 | 标记 `partial`，只建产物索引，不阻断扫描；日志按 mod 汇总 |
| 某 mod 配方量超过 5 万条 | 正常处理，但对该 mod 的卡片列表强制分页，并在日志提示「该 mod 配方数量异常，建议确认」 |
| 点击配方卡片但源 jar 已被用户移动/删除 | 捕获 `ENOENT`，toast「源文件已失效，无法载入完整配方」，卡片仍可用于浏览摘要 |

# 七、代码质量要求

1. TypeScript `strict` 通过，`tsc --noEmit` 零错误，`eslint` 零 error
2. 主进程 / preload / 渲染进程职责清晰，所有跨进程调用有完整类型定义（在 `src/shared/ipc.ts` 统一定义 channel 与 payload 类型）
3. 不使用 `any`（确需时用 `unknown` + 类型守卫）
4. 所有 IPC 处理函数包裹 try/catch，异常统一转成 `{ ok: false, error: string }` 返回，不向渲染进程抛未捕获异常
5. 组件拆分合理，单个文件不超过 300 行；状态集中在 zustand store，禁止 prop drilling 超过 3 层
6. 关键算法（形状裁剪、拼音索引、搜索排序、jar 解析）必须写单元测试（vitest），至少覆盖：空网格、单物品、满 3×3、多音字、全拼/首字母/ID 混合查询
7. 提供 `npm run dev` / `npm run build` / `npm run test` 脚本，README 写明启动步骤

# 九、禁止事项

1. **禁止**用一张巨大的表硬编码「模组 → 配方类型」，必须以 schema 注册表形式组织，且支持运行时扩展
2. **禁止**用 HTML5 原生 `dragstart/dragover` 实现拖拽（幽灵图定制与跨区域碰撞不可控）
3. **禁止**在渲染进程直接 `require('fs')` 或开启 `nodeIntegration`
4. **禁止**一次性把 41,000 条物品渲染成 DOM 节点
5. **禁止**在未做语法校验的情况下写盘
6. **禁止**用 `alert()` / `confirm()` 原生弹窗，一律用自绘 UI 组件
7. **禁止**留 `TODO`、占位函数、`console.log('not implemented')`
8. **禁止**为追求"支持所有模组"而编造你不确定的配方字段名——不确定就交给 `event.custom()` 兜底
9. **禁止**把物品图标从 jar 解压到整合包目录内（污染用户目录），只能放 `userData`
10. **禁止**把整合包全部配方 JSON 全量常驻内存或写入缓存（15 万条全量 JSON 必然 OOM），只能存摘要 + 惰性读取
11. **禁止**为「制作/用途」两个 Tab 分别写一套解析逻辑——必须是同一份倒排索引的两次查询
12. **禁止**在配方浏览视图里阻塞主线程读取 jar（必须异步 + 骨架屏）
13. **禁止**用一套统一模板生成所有模组的语法糖调用——各模组参数形态与语义差异极大（见 3.6.2 差异表），必须按 schema 渲染
14. **禁止**在未检测附属模组的情况下生成 `event.recipes.<ns>.<method>()`——附属未装时该调用在游戏里是 `undefined`
15. **禁止**因为"这个模组没内置支持"就隐藏其可用配方类型——只要配方库里有该 type 的样本，就必须让它可编辑
16. **禁止**把内置库中的 API 写法当作事实——未经 ProbeJS 验证的语法糖签名，必须在日志与预览中标明「未在本包验证」
17. **禁止**为了"代码好看"而牺牲可运行性：拿不准时一律降到数据包 JSON，不允许赌一把语法糖
18. **禁止**用名称首字、纯色块、统一符号、emoji 作为物品的常规图标——侧边栏与槽位必须显示从 jar 提取的真实 16×16 贴图
19. **禁止**接受大面积图标缺失：若占位图比例超过 5%，视为图标提取器有缺陷，必须修复（优先检查 `parent` 继承链与 `textures/` 路径拼接）
