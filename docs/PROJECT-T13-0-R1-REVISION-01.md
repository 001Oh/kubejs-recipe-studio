### 2.2 分析推断（本稿的判断，非文件原文）

- 「恰好 1 条」与 FIX-01 的冲突在于：FIX-01 修好后，一次预览可能**合法地**触发多次层重建（例如 `syncPluginLayer` 与 `refreshEffective` 各走一次，或一次读取里既有 `invalidateSnapshot` 又有 `factsKey` 变化）。把它判死为「>1 条即作废」会让**修复本身**变成不可验收项。
- 因此正确判据不是「次数」，而是「**每条重建都能对应到一个已知触发点**」。这就是「≥1 且可解释」的实质。

## 3. 修订项 R1-A：把「恰好 1 条」改成「≥1 且可解释」

### 3.1 新判据（建议原文替换 RT-01 步骤 7 / RT-02 同位置）

> **重建计数判据**：统计「基线锚点之后、观测点之前」的 `五层合并完成：生效 N 个` 日志行，记条数为 `C`。
>
> - `C = 0` → **不通过**（预览/选择路径没有走 `ensureSchemas()`，属缺陷）。
> - `C ≥ 1` → 进入**可解释性核对**：每一条都必须能归因到下表中的一个触发源；归不上的条目即为「不可解释」。
> - 只要出现**任何一条不可解释**的 `五层合并完成` → 本次证据**作废并重跑**（说明有未受控入口介入）。
> - 全部可解释 → **判通过**，并在证据里列出 `C` 与每条归属。

### 3.2 可解释性归属表（新增，判定程序的核心）

| 触发源 | 机制 | 判定线索 |
|---|---|---|
| T1 预览路径自身 | `codegen:preview` → `loadSchema(typeId)` → `schemaById` → `ensureSchemas` | 时间戳紧邻预览请求；`factsKey` 与前次相同或已变化均可 |
| T2 `factsKey` 变化 | 路径/记录数/类型数/附属数/模组数任一变化 | 同一时刻有换包/扫描完成/插件变更日志 |
| T3 插件层同步 | `loader.syncPluginLayer()` = `replaceLayer` + `invalidateSnapshot` + `refreshEffective` | 紧随 `plugins:list`（**有刷新副作用**）或插件启用状态变化 |
| T4 快照戳未命中 | 上次写入失败或 `ok!==false` 但 `state==='failed'`（FIX-03 语义） | 存在 `loadFailure` 记录 |

> 若一条 `五层合并完成` 同时可归入多个源，**只记一次**，但必须写明主因。

### 3.3 为什么不再要求「恰好 1 条」

| 场景 | 「恰好 1 条」的后果 | 「≥1 且可解释」的后果 |
|---|---|---|
| FIX-01 修复后一次预览触发 T1 + T3 | 判为 >1 → 证据作废 → **修复本身无法验收** | 两条均可归因 → 通过 |
| 插件读取失败期间反复装配 | 每次读取都完整装配 → 条数远大于 1 | 每条归因 T4 → 通过，但需记录次数作为观察项 |
| 真缺陷（预览根本没走 `ensureSchemas`） | `C=0` → 抓得住 | `C=0` → **同样抓得住** |

结论：新判据**没有放松对真缺陷的检出**，只是不再把「合法多次重建」误判为失败。

## 4. 修订项 R1-B：差异源（对应 D-19，仍待决策）

### 4.1 三个候选（沿用 D-19 原文，未改）

| 备选 | 内容 | 代价 |
|---|---|---|
| **A** | 允许改 jar（先 `cp -r` 再改） | 成本高、易出错 |
| **B** | 只允许改包内插件目录 | 差异源弱于 A，但可观测、可回滚 |
| **C** | 放弃 RT-01/02，改做「换包整体验收」 | 失去 REM-01 的针对性证据 |

### 4.2 本稿判断（建议，非决定）

**建议维持 B**（当前 R1 已按 B 落地：包内嵌插件），理由：

1. B 的差异源直接作用在 `plugin` 层，而 `plugin` 层是 `ensureSchemas()` 唯一与「包」强耦合的层（`builtin` 来自 `PILOT_SCHEMAS`，`pinned` 来自用户数据）。
2. A 需要改 jar 内容，与 `.cache/pc7-pack-1112` 的「**禁止就地改写**」纪律直接冲突，必须 `cp -r` 出副本，成本与出错面都更高。
3. C 会让 REM-01 失去针对性证据，而 REM-01 是台账里少数能证明「换包生效」的条目。

> **但这是建议，不是决定。** D-19 仍为「待决策」，本稿不改变该状态。

### 4.3 RT-02 判据的最小修正

原 RT-02「切包后复用原 uid」不可行（F5）。建议判据改为：

- **不依赖原 uid**：切包后**重新从 B 包自身的配方列表**取一条 uid（`jar:<名>#<entry>` 优先，因为它是唯一跨包稳定的形态）。
- 若 B 包无 jar 来源配方 → 记为「环境不具备」，不得判通过。
- 观测点改为「选中该 uid 后，`selectSchema` 是否按**试点类型优先**给出 schema，且该 schema 来自 B 包的 `plugin` 层」。

## 5. 修订项 R1-C：Q-02 语义（四分已存在，缺判据落点）

### 5.1 现状事实

原文已四分（`①正常空 / ②目录不存在 / ③存在但读不出 / ④provider 抛异常`），并标注 ①②③ 都返回空数组但语义不同；④ 已由 RV1-003 处理（保留旧层）。**缺的是 ②③ 的判据落点与推荐方案。**

### 5.2 建议（推荐 C）

| 情形 | 期望行为 | 判据（可观察） | 依据 |
|---|---|---|---|
| ① 目录正常且为空 | 插件层为空 | 插件面板显示「0 个插件」，且**无** WARN | 确实没装插件，空是正确结果 |
| ② 目录不存在 | **保留旧层** + WARN「插件目录不存在」 | 旧插件类型仍在；日志有 WARN；`getPluginLoadStatus()` 报 `missing` | 与 ③ 同属「读不到」，「被误删」不等于「主动不装」 |
| ③ 目录存在但读不出 | **保留旧层** + WARN「读取失败」 | 同上，状态报 `failed` | 用户没删插件，不能表现成「全部消失」 |
| ④ provider 抛异常 | 保留旧层 | 已由 RV1-003 覆盖 | 现状已实现 |

**推荐 C 的实质**：把「①=确实没有」与「②③=读不到」分开；②③ 一律不清层。

**代价（必须写明）**：若用户**真的删掉**插件目录且此时读取仍失败，旧类型会持续存在，用户可能以为没删掉。缓解：WARN 必须出现在设置页可见位置，而不是只进日志。

> 这与代码现状**不一致**：当前 `listPluginFiles` 对 `②③` 都 catch 成 `[]`，等价于「没有插件」→ 层被清空。**本稿不改代码**；如需落地属 A2，且与 `FIX-02`（`{ok:false}` 语义）同源。

### 5.3 必须四分、不得合并的理由（引用原文）

①②③ 最终都产生「空数组」，但不能因此认定三者语义相同 —— ① 是「确实没有」，②③ 是「读不到」。这正是 ④ 已被区别对待、而 ②③ 没有的原因。
