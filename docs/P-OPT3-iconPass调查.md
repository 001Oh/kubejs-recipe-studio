## 2. 当前 iconPass 机制与「重复枚举」的真实来源

```
scanItems
 └ runJarPool: 每 jar 调一次 listEntries（拿到完整条目表）
      └ 返回 assetEntries（已按 lang/models/textures 过滤后的名字列表）
 └ resolveMissingIcons(misses, iconDir, entriesByJar)
      ├ 用 entriesByJar 建 textureIndex / modelIndex     ← 不再 listEntries（已复用）
      ├ 轮 0..3：readEntriesByJar(pending) → readMany(jar, names)
      └ 贴图轮：readEntriesByJar(textureWanted)
```

**关键事实：`listEntries` 已经没有被 iconPass 重复调用。** 条目清单由 `runJarPool` 创建、随 `entriesByJar` 传入；
iconPass 只用它建内存索引。测量期 mock 的 `listEntries` 调用数为 **0**（170 次全部是 `readMany`）。

真正重复的是 `readMany`：`src/main/scanner/zip.ts:112` 的实现每次都**顺序回调归档里的全部条目**再挑需要的读，
所以每次调用成本 ≈ 该 jar 的条目总数，与被读条目数几乎无关。iconPass 因此为 3.26MB 数据遍历了 **567,992 个条目**。

## 3. 为什么会有多轮，能否合并

| 轮 | 输入 | 目的 | 实测 |
| --- | --- | --- | --- |
| 0 | 每个 miss 的直接候选模型（`assets/<ns>/models/{item,block}/<stem>.json`） | 找到模型并取 `textures` 引用 | 91 个 jar / 6,113 条目 |
| 1 | 轮 0 解析出的 `parent` 条目 | 父模型可能带 `textures` | 39 个 jar / 394 条目 |
| 2 | 轮 1 的 `parent` | 祖父模型 | 6 个 jar / 13 条目 |
| 贴图 | 选中的贴图条目 | 取 PNG 字节 | 34 个 jar |

后续轮次确实**依赖前序轮次的输出**（parent 只有读过模型才知道），无法预先合并；要一次读完就必须预读某 jar 的
全部模型。按快照统计：104 个有 miss 的 jar 共有 **46,496 个模型**，而当前实际只读 6,520 个。
把 3 轮合并成 1 轮最乐观只能少 **45 次 `readMany`（≈47k 条目 ≈0.7s）**，却要多读并解析约 4 万个模型 JSON。
因此**合并轮次是净负收益**，未实施。

## 9. 已知限制与风险

1. iconPass 的 8–9s 几乎全是「每次 `readMany` 扫一遍中央目录」的固定成本，只有改 ZIP 读取方式才能消除。
2. OS 页缓存与机器负载使同代码的 items 时间在 81–123s 之间波动，跨会话比较无效。
3. 快照测量复用同一 miss 集与 `entriesByJar`，能保证各变体输入一致，但不能反映池阶段本身的耗时变化。
4. 未实现、也未验证「预读某 jar 全部模型」的实际表现（只按条目数与字节量估算为净负收益）。
5. 未在 CI/第二台机器验证。

## 10. 下一步建议（仅建议，未实施）

**P3（完整版）：ZIP「列一次 + 随机读」**——用一次 `listEntries` 拿到中央目录后，对同一 handle 按需
`openReadStream(entry)`（或改用支持随机访问的读取层），把一次冷启动的 **1,489 次归档遍历**压到 295 次。

- 预期：iconPass 8–9s 中约 7–8s 可消除；配方阶段与 detect 也会受益（P-OPT1 测得 1,447,083 次 entry 回调）。
- 风险：需要动 `zip.ts` 的句柄生命周期与 `readMany` 语义（现行注释明确「不复用句柄」），属架构级改动，须单独评审与回滚方案。
- 在此之前不建议再做 iconPass 的局部微调（已证明收益 <1s）。
