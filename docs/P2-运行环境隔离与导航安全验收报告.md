## 2. 修改前的环境数据目录结构（只读检查结论）

| 项 | 修改前的事实 |

## 3. 修改后的目录策略

优先级（命中即用）：

| 顺序 | 来源 | 目录 | 用途 |
| --- | --- | --- | --- |
| 1 | `STUDIO_USER_DATA` 环境变量（支持相对路径，按 `cwd` 解析） | 由调用方指定 | 自动化测试 / 调试 / 双环境并行验证 |
| 2 | 命令行 `--user-data-dir[=…]` | Electron 解析后的值 | 兼容既有 E2E 脚本，**不追加 -dev** |
| 3 | 开发态（`app.isPackaged === false`） | `<默认 userData>-dev` | 开发调试，稳定不随机 |
| 4 | 正式安装版 | 默认 userData（**原位置不变**） | 兼容既有用户数据 |

- 实际默认值（本机实测）：`C:\Users\qituo\AppData\Roaming\kubejs-recipe-studio`；开发态为 `…\kubejs-recipe-studio-dev`。
- 只有 dev / env 两种来源会 `app.setPath('userData', …)`；prod / cli 保持 Electron 已解析的路径，**不改动既有用户数据位置**。
- 时序：`index.ts` 第 36 行 `applyUserDataDir(app)` 在 `requestSingleInstanceLock()` 与 `whenReady()` **之前**执行；启动日志会打印 `数据目录（dev/prod/env/cli）：<路径>`，便于现场排查。

### 3.1 首次运行 / 升级 / 已有数据兼容

- 正式版路径未变 → 升级后仍读同一 `uiState.json`、缓存、备份；不迁移、不清空。
- 开发态首次启动会新建 `-dev` 目录（空缓存 → 重新扫描），**不读取也不写入**正式版数据。
- 不存在「dev 数据导入 prod」的逻辑。

## 4. 单实例锁与数据目录的关系

- Electron 的单实例锁文件位于 userData 目录内，因此目录隔离 = 锁隔离。
- 实测（`.cache/p2-env-smoke.mjs`）：
  - A、B 两个实例分别使用 `STUDIO_USER_DATA=…p2-ud-A` / `…p2-ud-B` → **同时存活**，各自 1 个页面；
  - 同环境再启动 A2 → **退出码 0（约 0.5s）**，A 仍存活、页面数仍为 1，B 不受影响；
  - dev（不设环境变量）→ userData 为 `…kubejs-recipe-studio-dev`，与 A/B 均不同；
  - 三个实例关闭后退出码均为 **0**（修复 §6.4 后复测）。

## 5. 缓存 / 配置 / 日志 / 备份的隔离验证

- 结构上：全部经 `studioRoot()` 派生（§2 表），改 userData 即整体隔离。

## 6. 导航守卫的修改前后行为

### 6.1 修改前（P1）

- `isAllowedNavigation` 用 `url.href.startsWith(pathToFileURL(rendererDir + '/'))` 判断；
- 解绑用 `win.once('closed', disposeNavGuard)`，解绑函数内部访问 `win.webContents`。

### 6.2 修改后（P2）

- **路径判定改为词法规范化**：`fileURLToPath`（解码 `%2e%2e`、`%5c` 等）→ 双端 `path.resolve`（Windows 下 `toLowerCase`）→ `path.relative` 判断包含关系；`..`、绝对路径、相似前缀目录（`renderer-evil`）、NUL 字节全部拒绝。
- `file://` 只接受 `host === ''`（UNC 与外部 host 拒绝）；非 file 协议一律拒绝；matcher 解析失败即拒绝。
- 开发态仍只允许与 dev server **同源**的 http(s)。
- 解绑改为缓存 `webContents` 引用 + `isDestroyed()` 判断 + `try/catch`，并挂在窗口 **'close'**（销毁前）而非 'closed'。
- 拦截时仍记 `logger.warn('UI', '已拦截页面导航：<url>')`，行为未变。

### 6.3 路径边界测试清单（`tests/main/navigationBoundary.test.ts`，13 条）

| 类别 | 用例 |
| --- | --- |
| 目录包含 | 目录自身/子文件允许；`renderer-evil`、`renderer2` 拒绝；父目录/兄弟目录拒绝；NUL 字节拒绝 |
| Windows | 盘符大小写等价允许；不同盘符拒绝 |
| 编码穿越 | `%2e%2e`、`..%2f`、`%2f..`、`%5c`、`%5C` 一律拒绝 |
| 双写编码 | `%252e%252e` 解码为字面量，仍在目录内（允许）——验证不会越界 |
| 合法形态 | 带 `?query#hash` 的页面、`assets/` 子文件允许 |
| 协议/主机 | UNC（`file://server/...`）、非本地 host、`javascript:`、`data:`、`ftp:`、`app-icon:`、畸形 URL 全部拒绝 |
| 开发态 | 同源允许（含 hash）、异端口/异主机拒绝、file:// 白名单仍生效 |
| 销毁安全 | 守卫解绑时 `webContents.isDestroyed() === true` → 不调用 `removeListener`、不抛异常（P1 缺陷回归用例） |

### 6.4 修复：主进程 `Object has been destroyed`（P1 回归）

- **现象**（用户截图 + 复现）：关闭窗口时弹出「A JavaScript error occurred in the main process」，栈为
  `TypeError: Object has been destroyed at BrowserWindow.<anonymous> (out/main/index.js:253)` ← `onceWrapper` ← `BrowserWindow.emit`。
- **根因**：P1 把 `disposeNavGuard` 挂在 `'closed'` 上，此时 `win.webContents` 已销毁，解绑函数访问它即抛错；异常发生在事件回调里 → Electron 弹出模态错误框 → **阻塞退出**（这也是 P2 冒烟里出现 `exitCode: null` 的原因）。
- **修复**：解绑函数缓存 `contents` 并在 `isDestroyed()` 时直接返回（try/catch 兜底）；`window.ts` 改为 `win.once('close', disposeNavGuard)`（销毁前触发）。
- **验证**：修复后 A/B/C 三实例关闭退出码均为 **0**；冒烟从「9 分钟且部分不退出」变为 **10 秒全部正常退出**；A 的日志中 `TypeError|Object has been destroyed` 计数为 **0**。
- **影响面**：仅主窗口关闭路径；不影响扫描、提交、备份。

## 11. 未完成事项

1. **正式安装版未实测**：本阶段禁止打包，因此「prod 分支在真实安装包中沿用原目录」仅由代码与单测保证（`isPackaged === true` → 不改路径），未在 `.exe` 上验证。
2. **两个真实「环境」是用环境变量模拟的**：A/B 用 `STUDIO_USER_DATA` 区分，而非「已安装版 + dev」双形态；锁隔离与目录隔离的机制相同，但形态差异未实测。
3. **符号链接未处理**：路径判定是纯词法（`resolve` 后比较），若 `out/renderer` 内存在指向外部的软链接，词法上仍判为「目录内」。当前渲染目录由构建产物生成、不含软链，风险低；如需彻底防护需 `realpath` 比对（会增加每次导航的磁盘 I/O），本轮不做，记为已知风险。
4. **`--user-data-dir` 显式传入时不追加 `-dev`**（为兼容 E2E）：若开发者手动用该参数指向 prod 目录，仍会共享数据——这是显式选择，不是默认行为。
